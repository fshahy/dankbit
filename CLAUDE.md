# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the Stack

```bash
# Start all services
docker compose up -d

# Rebuild after code changes
docker compose up -d --build

# Rebuild a single service (e.g. after editing dankbit_ws_batch.py)
docker compose up -d --build dankbit_ws

# Tail logs
docker compose logs -f
docker compose logs -f dankbit_ws

# Restart just the Odoo addon (no rebuild needed for Python changes to my_addons)
docker compose restart web
```

After first startup, install the Dankbit addon via Odoo UI: Apps → search "Dankbit" → Install.

**Required `.env` variables:**
```
DANKBIT_POSTGRES_DB=<db_name>   # any name; db1 is the development default
DERIBIT_KEY=<key>
DERIBIT_SECRET=<secret>
```
The `UID` and `GID` env vars are also needed so the `web` container writes files as the host user (dev default: `1000`/`1000`). `docker-compose.yml` sets `user: "${UID}:${GID}"` on the `web` service and `chown`s the Odoo data dir to that UID/GID before starting — the values must match whichever host user owns the bind-mounted directories, so Odoo's writes (filestore, logs) land with an owner the host can actually manage. Check with `ls -ln <bind-mounted dir>` if unsure. Setting it to `0`/`0` (root) is correct only when the production host directory itself is root-owned — it also means Odoo runs as root inside the container, a broader security surface than an unprivileged UID.

> **Production note:** `config/odoo.conf` contains `dbfilter = ^db1$` — update this to match the actual database name.
> **Production note:** production's `.env` uses `UID=0`/`GID=0` (root), unlike the dev default of `1000`/`1000` — see above for when that's the correct choice.

## Architecture

Two Docker services talk to a shared PostgreSQL database:

```
Deribit WS API ──► dankbit_ws (Python asyncio) ──► PostgreSQL
                                                        │
                   Deribit REST API ◄── Odoo cron       │
                                                        ▼
                                               Odoo 18 (web:8069)
                                                        │
                               ┌───────────────────────┤
                               │                       │
                        PNG charts                TradingView
                  /BTC-<EXPIRY>, /i/BTC-<EXPIRY>  /chart/BTC
```

**Trade data enters two ways:**
1. **WebSocket (primary):** `dankbit_ws_service/dankbit_ws_batch.py` — connects to Deribit, authenticates, fetches all BTC+ETH option instruments, subscribes to `trades.<instrument>.raw` channels in chunks of 400, inserts rows directly into PostgreSQL with `ON CONFLICT IGNORE` on `deribit_trade_identifier`.
2. **REST backfill:** `Trade.get_last_trades()` — runs nightly via cron (`dankbit_get_last_btc_trades_cron`, inactive by default); each run re-fetches every active (plus recently-expired, see `RECENTLY_EXPIRED_GRACE_MINUTES`) instrument's *full* retained Deribit trade history from scratch (`start_timestamp=0`) rather than resuming from the DB's latest known trade, so a WS outage earlier in the day can't leave a permanent gap before the WS's own most-recent captured trade. Duplicate inserts are silently dropped via the `deribit_trade_identifier` unique constraint, so re-fetching already-known trades is safe and cheap.

**PNG chart rendering:** Per-expiry routes like `/BTC-7MAY26` aggregate all trades for that expiry, compute a Black-Scholes portfolio delta and dollar-gamma (GEX = Γ × S²) curve, and return a PNG via matplotlib's Agg backend (`Figure + FigureCanvas`, never `pyplot` — server-safe). Overlaid lines: gamma peaks and bottoms (dashed black), delta=0 crossings (solid — green for "supply" [delta negative below, positive above], red for "demand" [delta positive below, negative above]).

**Zones chart (`/<instrument>/zones`):** a distinct plot mode — separates that instrument's trades since 00:00 UTC (via `options.day_window_start()` — the day boundary this and every other "00:00" trade window in this addon resets on; this briefly reset at Asia/Tehran midnight instead, confirmed at the time against Thales's own numbers, whose R/S/gamma reference didn't line up with ours under UTC — but was reverted back to UTC midnight per a later request from Thales's dev) into buy-side and sell-side (trade domain uses `("name", "=ilike", f"{instrument}-%")`, an anchored/left-prefix match — not a bare `ilike` substring match — so a query for one expiry can never pull in another instrument's trades), builds two independent `OptionStrat` payoff curves via `options.build_zone_curves()` (`long_call`/`long_put` for buys, `short_call`/`short_put` for sells — same payoff math as the combined-portfolio routes, just accumulated into two separate objects, plus the crossing-based auto-zoom below — same function `dankbit.bands` calls, see Models), and plots them together via `OptionStrat.plot_zones()`: green "Longs" curve, red "Shorts" curve, blue vertical line at index price — `plot_zones()` itself draws no text overlay. The `Seller Max Profit (SMP)`/`Buyer Max Loss (BML)`/`High Zone`/`Low Zone`/`Middle Zone` info is rendered as page HTML, alongside further per-expiry stats: `chart_png_zones` calls `options.zone_summary(STs, longs_curve, shorts_curve)` (module-level function, same extrema/box-boundary definitions as `dankbit.bands` — see Models) for `seller_max_profit`/`buyer_max_loss`/`high_zone`/`low_zone`/`middle_zone`/`high_resistance`/`low_support`, labeled on the page as `Seller Max Profit (SMP)`/`Buyer Max Loss (BML)`/`High Zone`/`Low Zone`/`Middle Zone`/`High/Resistance`/`Low/Support`, same `(SMP)`/`(BML)` convention the Gamma/Delta/Theta/Vega headers below use. Current price is not a factor in any of these: `high_zone`/`low_zone` are each curve's own highest/lowest zero-crossing (the Shorts curve's and Longs curve's max feed `high_zone`, their min feeds `low_zone`) rather than "the nearest crossing above/below index price" — a zone forms as soon as *either* curve has at least one crossing (a lone curve's crossing yields a degenerate same-price pair, rendered as a single price rather than a dashed range); only `None`/`"n/a"` if neither curve ever crosses zero. `middle_zone` is a third zone bounded by `seller_max_profit`/`buyer_max_loss` (min/max of the two) rather than any zero-crossing — always defined, since those two values are argmax/argmin over the full curve and don't depend on a crossing existing, unlike `high_zone`/`low_zone`. Then restricts that route's own `trades` to the single nearest expiry (mirroring `dankbit.bands`'s "next expiry only" restriction) and delegates the actual per-leg gamma/delta/theta/vega extrema computation to `options.per_leg_greeks()` — the single source of truth for this also used by `dankbit.bands`'s `gamma_band`/`delta_band` and by `forecast.per_leg_greeks()`, so this page, the persisted bands record, and the Thales Forecast engine can never quietly disagree on these numbers for the same trades. Gamma extrema are preceded in `zone_info_lines` by a violet-colored `Gamma` section-header line: `Buyer Call Gamma (BCG)`/`Buyer Put Gamma (BPG)` (price where the long-call/put gamma curve peaks, `argmax`) and `Seller Call Gamma (SCG)`/`Seller Put Gamma (SPG)` (price where the short-call/put gamma curve bottoms out, `argmin` — short positions carry negative gamma, so the relevant extremum is a trough, not a peak — same BCG/BPG/SCG/SPG abbreviations `dankbit.forecast.snapshot`'s `bcg_price`/`bpg_price`/`scg_price`/`spg_price` fields use) — plus, in their own block right below, the gamma value (not dollar-formatted, unlike the price lines) at each of those same 4 extrema (`{curve}[argmax/argmin index]`, the y-value at the point already located for the price line, not a separate computation) — shown as an absolute value divided by 1,000,000 and rounded (the sign is already conveyed by which side of the section it's on: peaks are long/positive, bottoms are short/negative), since these raw dollar-gamma numbers run into the hundreds of millions and the user copies them by hand into another tool — labeled `BCG Abs.`/`BPG Abs.`/`SCG Abs.`/`SPG Abs.`. Also computes each leg's delta-saturation price via `options.delta_saturation_price()` (calls saturate ITM at high S, puts at low S, independent of long/short, `fraction=DELTA_SATURATION_FRACTION`=0.9 — see below), preceded by a green-colored `Delta` header, labeled `Buyer Call Delta (BCD)`/`Buyer Put Delta (BPD)`/`Seller Call Delta (SCD)`/`Seller Put Delta (SPD)` (same abbreviations `dankbit.forecast.snapshot`'s `bcd_price`/`bpd_price`/`scd_price`/`spd_price` fields use), plus — in their own block right below — the portfolio-delta value at that same price, labeled `BCD Abs.`/`BPD Abs.`/`SCD Abs.`/`SPD Abs.` — shown as an absolute value divided by 10 and rounded to a whole number, same reasoning as the Gamma Value lines above (dividing by 1,000,000 there, 10 here, since delta values are already two to three orders of magnitude smaller). That value is interpolated off the underlying `delta.portfolio_delta()` curve at the saturation price rather than assumed to equal `fraction * curve edge` exactly, since `delta_saturation_price()` falls back to the `STs` edge (not a true 90%-threshold crossing) when the curve never reaches that threshold within this window — interpolating keeps the reported value correct in that fallback case too. Also computes, per leg, the price where portfolio theta ($/day — see `theta.py`, a new module mirroring `delta.py`/`gamma.py`'s `bs_*`/`portfolio_*` pattern; `bs_theta()` returns the annualized Black-Scholes theta ÷ 365, the convention traders quote, not the raw per-year value) is most extreme over the same price grid gamma/delta use — sign-flipped from gamma's peak/bottom split: long positions carry negative theta (decay cost), so their extremum is the trough (`argmin`, worst decay); short positions carry positive theta (decay gain), so theirs is the peak (`argmax`, best decay) — against the same next-expiry-only `long_calls`/`long_puts`/`short_calls`/`short_puts` recordsets gamma/delta reuse, with the same `r=0.0` convention as this page's other Greeks. Preceded by an orange-colored `Theta` header, labeled `Buyer Call Theta (BCT)`/`Buyer Put Theta (BPT)`/`Seller Call Theta (SCT)`/`Seller Put Theta (SPT)` (same abbreviations `dankbit.forecast.snapshot`'s `bct_price`/`bpt_price`/`sct_price`/`spt_price` fields use) — plus, in their own block right below, the theta value ($/day) at each of those same 4 extrema (`{curve}[argmin/argmax index]`, same pattern as the gamma/delta value blocks), labeled `BCT Abs.`/`BPT Abs.`/`SCT Abs.`/`SPT Abs.` — shown as an absolute value divided by 10,000 and rounded, same reasoning as the Gamma/Delta Value lines (dividing by 1,000,000 for gamma, 10 for delta, 10,000 here, since raw $/day theta values sit in between those two scales). Also computes, per leg, the price where portfolio vega (`vega.py`, a module mirroring `gamma.py`'s `bs_*`/`portfolio_*` pattern rather than `theta.py`'s — vega has no call/put distinction in Black-Scholes, so `bs_vega()` takes no `option_type`, same as `bs_gamma()`; returns raw vega / 100, the $-per-1-IV-point convention traders quote, mirroring `bs_theta()`'s /365) is most extreme over the same price grid — same peak/bottom split as gamma, not theta's flipped one: vega is always positive for a long option and always negative for a short one, so long legs peak (`argmax`) and short legs bottom out (`argmin`) — against the same next-expiry-only `long_calls`/`long_puts`/`short_calls`/`short_puts` recordsets and `r=0.0` convention as this page's other Greeks. Preceded by a blue-colored `Vega` header, labeled `Buyer Call Vega (BCV)`/`Buyer Put Vega (BPV)`/`Seller Call Vega (SCV)`/`Seller Put Vega (SPV)` (same abbreviations `dankbit.forecast.snapshot`'s `bcv_price`/`bpv_price`/`scv_price`/`spv_price` fields use) — plus, in their own block right below, the vega value ($ per 1 IV point) at each of those same 4 extrema, labeled `BCV Abs.`/`BPV Abs.`/`SCV Abs.`/`SPV Abs.` — shown as an absolute value divided by 100 and rounded, same reasoning as the other Value lines (raw portfolio-vega values sit in the low thousands, an order of magnitude below theta's ten-thousands and well above delta's tens, so /100 keeps the displayed number in the same easy-to-copy 2-3 digit range). Unlike every block above Theta, Theta and Vega are kept in a *separate* `right_info_lines` list rather than appended to `zone_info_lines` (passed into the shared template under the `theta_info_lines` context var name, which carries both Greeks), and rendered in its own top-right `.zone-info-right` overlay (mirrors `.zone-info`'s styling, just `right: 12px` instead of `left: 12px` for the box position — text inside stays left-aligned, same as `.zone-info`) — so it sits to the right of the PNG instead of stacking underneath Gamma/Delta on the left. All of this is assembled into `zone_info_lines`, where every line is a `{text, color}` dict rather than a plain string (color `None` for the default black styling; only section headers set one), rendered by the template via `t-att-style` on that per-line `<div>` (grouped into 7 blocks — price extrema; boxes; intersections; gamma peak/bottom prices; gamma peak/bottom values; delta-saturation prices; delta-saturation values — separated by blank spacer lines, a `" "` non-breaking space since a truly empty/whitespace-only `<div>` can collapse to zero height) and passed to the shared `dankbit_page` template's `zone_info_lines` context var, rendered as a fixed top-left overlay div (`.zone-info`, `user-select: text` so it's copyable, only shown when that var is present, so every other PNG route using `dankbit_page` is unaffected). A separate bottom-left annotation (added by `chart_png_zones` itself, drawn inside the image via `ax.text()`) shows the long/short trade counts since 00:00 UTC. **Auto-zoomed x-axis:** the configured `from_price`/`to_price` settings are only used for an initial wide pass to locate where the Longs/Shorts curves cross (linear interpolation on the sign change of `longs.payoffs - shorts.payoffs`, same technique as the delta=0 crossing finders); the curves are then rebuilt over `[leftmost_crossing - margin_below, rightmost_crossing + margin_above]` at the same `steps` resolution, so the rendered chart is tightly framed around the relevant region instead of the full (much wider) configured range. Margin is asset-dependent: BTC uses ±$2000; ETH uses ±$100 (ETH's much smaller price scale made the ±$2000 BTC margin blow out the auto-zoom). Falls back to the original wide range if the curves never cross.

**Single-leg delta/gamma routes (`/<instrument>/lp`, `/lc`, `/sp`, `/sc`):** four routes, one per leg type (long put, long call, short put, short call) — `_chart_png_single_leg(instrument, leg_key)` is the shared implementation, dispatched via `_LEG_ROUTES[leg_key]` (`direction`/`option_type` domain filter, which `OptionStrat` leg method accumulates trades, route label, and delta-saturation `fraction`/`side` — see below). Same domain convention as `chart_png_zones` (anchored `=ilike` instrument match, trades since 00:00 UTC), but restricted to that one direction+option_type combination and built over the **full configured price range** (`from_price`/`to_price`/`steps`), not the crossing-based zoomed window `/zones` uses — matching `chart_png_hours`/`chart_png_all`'s style instead, including their `r=0.05` risk-free rate for `delta.portfolio_delta`/`gamma.portfolio_gamma` (deliberately *not* `r=0.0`/zoomed-grid like `dankbit.bands`). `obj.plot()` renders the same delta+gamma dual-axis chart as those routes; the gamma peak/bottom + delta=0 crossing overlay is factored into `_annotate_gamma_delta_crossings(ax, STs, market_deltas, market_gammas)` (shared by all 4 routes, so they don't each carry their own copy of that block). A solid green `axvline` additionally marks the delta-saturation price from `options.delta_saturation_price()` — see `options.py` below — labeled with its price, drawn after the standard overlay.

**TradingView chart:** `/chart/BTC` and `/chart/ETH` serve a Lightweight Charts v4 page with live Binance spot candles (proxied server-side) and price lines refreshed on `dankbit.refresh_interval` — except the yellow/teal zones boxes and the Bands lines (High/Resistance, Low/Support, Gamma Band, Smart Liquidity), which both refresh on their own dedicated `dankbit.zones_box_refresh_interval` setting (default 3600s/1h, see Settings fields below) — Bands was moved onto this same slower interval (off the general `refresh_interval` it used to share with everything else) since its underlying `dankbit.bands` rows only ever change once per hourly `compute_snapshot()` cron tick, so polling faster than that just re-fetches identical data; keeping both on one shared interval also cuts requests as this addon gets more concurrent users:
- Gamma Horizon lines — up to ~8 horizontal `series.createPriceLine` levels (`gammaHorizonLines`), one per term-gamma horizon, from `/api/gamma-horizon/<asset>` (`gamma_horizon_json` in `main.py`). **Replaced the former Weekly/Monthly/All/Daily (24H)/Daily+1 (24H) delta=0 line sets and the "S/D" checkbox** (removed together with the `show_daily_lines`/`show_weekly_lines`/`show_monthly_lines` settings — the `/api/delta-zero*` routes themselves still exist, just no longer consumed by any page). Off by default, toggled by the "Gamma Horizon" checkbox (see TradingView Chart Notes). Each horizon — **D1** (tomorrow's expiry), **W** (the next 3 non-monthly Fridays), **M** (the next 3 monthly last-Fridays, December excluded), **YE** (December's last-Friday) — is computed independently: that expiry's own trades (hourly-aggregated in SQL, `iv <> 0`, `deribit_ts <= NOW()`), each trade-hour weighted `0.40 + 0.60 * 2^(-age_hours / half_life)` (half-life 24h/6d/15d/75d for D1/W/M/YE — a longer-dated expiry accumulates flow over weeks, so its older trades decay slower; D1 additionally hard-drops any trade older than a 72h `max_age_hours` cutoff, the only horizon with one), fed into independent buyer-side and seller-side `gamma.portfolio_gamma()` curves (`r=0.05`) over an adaptive price grid; `_gamma_horizon_peak()` takes each side's strongest-|gamma| price and the level drawn (`price`) is the midpoint of the buyer/seller peak prices, with per-side `buyer_price`/`seller_price`/`buyer_strength`/`seller_strength` also returned (`0.0`/absent-and-skipped for a side with no usable curve, same convention as `options.per_leg_greeks()`'s missing legs, never a grid-edge value). Display-only — **no persistence, not read by Forecast/Bands/Smart Liquidity/Greek Flow/Signal Bot**. The response's `trade_count` feeds the footer's `N trades` when this checkbox is on (see Footer status below). Per-horizon color/style/width, weekly & monthly line-count caps (0–3), and an expiry-date-label toggle are configurable in the Settings modal's own "Gamma Horizon" section, persisted per-browser to `localStorage` under `dankbit_gamma_horizon_settings` (defaults: D1 `#ff9800` dashed w1, W `#7e57c2` solid w1, M `#00acc1` dashed w1, YE `#d81b60` solid w2; all visible, both counts 3, labels on).
- Bands lines (3) — `High/Resistance` (green, `#2e7d32`, solid), `Low/Support` (red, `#c62828`, solid), and `Gamma Band` (light violet, `#c9a0dc`, **dashed** — `LightweightCharts.LineStyle.Dashed`), `addLineSeries` on the **default/main price scale** (no `priceScaleId` override) since these are plain BTC/ETH price levels, not dollar amounts — they render directly alongside the candles. Sourced from `/api/bands/<asset>`: one point per **instrument** stored in `dankbit.bands` (see Models — one continuously-refined-then-frozen record per expiry, not a time-series of polls), positioned at that instrument's own expiration time rather than a poll timestamp — so these are term-structure-style lines connecting each expiry's final value to the next expiry's, not a history of one expiry's value changing over wall-clock time. `Gamma Band` is the average of that expiry's 4 gamma extrema (Buyer Call/Put Gamma (BCG/BPG), Seller Call/Put Gamma (SCG/SPG) — see Models, `dankbit.bands._compute_asset`'s `gamma_band`), the same 4 numbers the `/<instrument>/zones` PNG page's info overlay shows. The API response also carries `delta_band` — the average of that expiry's 4 delta-saturation prices (see `options.delta_saturation_price()`) — but it is deliberately **not drawn** on this chart (no `deltaBandSeries` in the template); it's computed and persisted for later use, not currently rendered. The endpoint derives each point's `t` via a single grouped lookup against `dankbit_trade` (`SUBSTRING(name FROM '^[^-]+-[^-]+')` to recover the instrument prefix, `MIN(expiration)`) rather than parsing the instrument string's day-suffix and assuming a settlement hour — raw SQL, so it still finds archived (past-expiry) instruments' trades despite the ORM's implicit `active=True` filter, since those rows must keep contributing a fixed historical point. Connected point-to-point by the line series. Shown on **every timeframe** (1h/4h/1d); `setTf()`/`init()` call `refreshBands()` on every timeframe switch. High/Resistance and Low/Support points additionally carry a `+`/`-` `setMarkers()` label (via `high_resistance_positive`/`low_support_positive` — see Models) showing whether the payoff *at* that intersection sits above or below the zero-payoff line, since the crossing's x-price alone doesn't say — `size: 0` hides the marker's shape glyph so only the text renders, colored to match its own line. `/api/bands/<asset>` additionally always covers all `TRACKED_EXPIRY_COUNT` active instruments now, filling in a not-yet-session-confirmed expiry with a synthesized, non-persisted "provisional" reading rather than omitting it — see the "Bands" checkbox below for the dashed continuation series that renders those.
- Zones boxes (2, plus a 3rd Seller Max Profit/Buyer Max Loss box — see below; toggled together by the "Zones" checkbox, TradingView Chart Notes below — checked by default) — filled rectangles (`#fbc02d`, 25% opacity fill, matching top+bottom border lines) marking the top and bottom zero-crossing zones for the **nearest** active expiry only (see Models, `get_box_n`/`TRACKED_EXPIRY_COUNT` for how later expiries are still tracked, just without a box). The 4 box-boundary fields themselves are **not** read from stored history — sourced live from `/api/zones-box/<asset>`, which calls `dankbit.bands.get_box()` to compute fresh on every request via `_compute_asset()` (see Models: nothing reads box-boundary history, only the latest value is ever drawn). `get_box()` computes fresh via `_compute_asset()` on every call but never persists anything (see Models, `get_box`) — the Bands lines' per-expiry history, for every tracked expiry including this nearest one, is fed *solely* by the hourly `compute_snapshot()` cron (see Models, `_persist_extrema`); no browser action, on this endpoint or any other, ever writes to `dankbit.bands`. The boxes' own visual state is never affected by the cron either way — box-boundary fields are recomputed fresh on whatever request (browser or cron) triggers `_compute_asset()`, but only the browser's request result is ever rendered; the cron's result is only ever persisted, never displayed. Each box is built from two `addBaselineSeries` (`aboveBoxSeries`/`belowBoxSeries` — a flat top-price line filled down to a `baseValue` bottom price) plus a plain `addLineSeries` for the bottom edge (`aboveBoxBottomLine`/`belowBoxBottomLine`), since `addBaselineSeries` only strokes its top edge. Top/bottom of each box are `max`/`min` of that side's two zero-crossing prices (`short_zero_above_price`/`long_zero_above_price` for the top box, `short_zero_below_price`/`long_zero_below_price` for the bottom box) — despite the field names, these are each curve's own highest (`*_above_price`) or lowest (`*_below_price`) zero-crossing, not "the nearest crossing above/below current index price" (see Models, `_compute_asset`). `setBoxData()` (in `dankbit_templates.xml`) draws the full rectangle when both a top and bottom price exist and differ; if only one curve contributed a crossing, or both coincide (a zero-height box), it instead draws a single line at whichever price is available (reusing the box's own bottom-edge line series) rather than dropping it silently; only clears both when neither curve crosses zero at all (a `0.0` value on **both** sides). Time span is `[now - 10 days, expiration]` — the right edge is that expiry's own real settlement time (Deribit's `expiration_timestamp`, e.g. 08:00 UTC / 10:00 CEST — read off `dankbit_trade.expiration` via `_compute_asset()`, not assumed/hardcoded), so the box now visibly runs all the way out to when the trades it's summarizing actually stop mattering, rather than stopping at "now". The left edge is a flat 10 days back from the browser's current wall-clock time (`Date.now()`, tz-shifted like every other timestamp on this chart), recomputed on every poll rather than fixed to a stored tick. Shown on **every timeframe** (1h/4h/1d), same as the Bands lines.
- Seller Max Profit / Buyer Max Loss box (3rd box, teal) — same mechanism (`addBaselineSeries` + bottom-edge `addLineSeries`, `setBoxData()`'s single-line fallback when top/bottom coincide) and the exact same `fromTime`/`toTime` as the yellow box above, since both come from the same `/api/zones-box/<asset>` response for the nearest expiry — `smpBmlBoxSeries`/`smpBmlBoxBottomLine`. Top/bottom are `max`/`min` of `seller_max_profit` (price where the Shorts payoff curve peaks) and `buyer_max_loss` (price where the Longs curve bottoms out) — see Models, `dankbit.bands`. No separate endpoint: `seller_max_profit`/`buyer_max_loss` were already computed by `_compute_asset()` as a side effect of the same `get_box()` call the yellow box uses, just added to `/api/zones-box/<asset>`'s JSON payload.
- Thales Forecast candles ("Thales Forecast" checkbox) — **Delta Chart only**, unchecked by default, after "Bands"; **restricted to the 4h timeframe** (`updateForecastVisibility()`, called from `setTf()` and at page init, shows/hides `#forecast-toggle-wrap` — starts hidden inline — based on `INTERVAL === '4h'`; `refreshForecast()` itself also gates on that condition so a stray poll can't redraw it off-timeframe). `updateForecastVisibility()` null-checks `#forecast-toggle-wrap` before touching it rather than assuming the element exists — a defensive leftover from when the since-removed Gamma Chart shared this same template/JS but didn't render that element. A full port of Thales's "Thales Bands" Pine indicator's forecast-candle engine (`controllers/forecast.py`) onto Dankbit's own live-computed per-leg Greeks, in place of Thales's manually-typed-in daily CSV rows (a companion HTML data-entry tool, "Thales Offline Data Builder", is what a human uses to feed that Pine script by hand — Dankbit needs no such tool since it already computes the equivalent numbers live). **Fully deterministic** — there is no GBM/random component anywhere in this engine (matching the source script, which has none either); every candle is a direct function of the current Greeks, real recent price action, and time-of-day/day-of-week, not a sampled realization. Runs out 18 4h-spaced candles (72h — `simulate_forecast`'s `hours_ahead=72` default), widened from Thales's own `forecastCandleCount` default of 6 candles/24h, since nothing in the engine assumes a specific cutoff — the per-step decay terms (`0.75 ** step`/`0.82 ** step`/etc.) just keep tapering further out regardless of horizon length. Sourced from `/api/forecast/<asset>` (`forecast_json` in `main.py`), rendered as an `addCandlestickSeries` (`forecastSeries`), light red/green by default (`#a5d6a7`/`#ef9a9a`, wicks `#66bb6a`/`#e57373`) to stay easily distinguishable from the real candles' own teal/red (`#26a69a`/`#ef5350`) at a glance. Entirely inert (zero impulse, no confidence floor) whenever the synthetic engine produces no level for that side.
  - **No future-known levels, unlike Thales.** Thales's own rows are manually dated, entered in advance up to a known expiry, so its forecast loop interpolates between a "current" and a "future" row that are both already-known data points. Dankbit has no foreknowledge of tomorrow's Greek levels, so there is only ever one "current" set of levels (top/low/gamma/curve/theta averages) — held constant across every forecast candle. The only thing that varies over real elapsed time is the history feeding the Gamma-Band Consensus engine's slope math (see below).

Bucket size was tightened from an initial 4h (matching the forecast candle's own spacing) down to 1h specifically for Greek Flow (see below) — its whole premise is detecting scan-to-scan Greek trend *within* the formation of one 4h forecast candle, which needs history spaced tighter than that candle's own step; `gamma_band_consensus`'s slope math benefits too, since it already normalizes "per real elapsed hour" and just becomes more responsive with tighter-spaced points, not incorrect with wider ones.

The Quadrant Behavior Engine (off by Thales's own default anyway), the newer version's full Regime-Adaptive Coefficient blending (weekday/weekend/low-volume/high-volume weight interpolation across ~7 factors — this port still only blends the pull/shock multipliers, not the gamma/curve/theta center weights), its granular per-phase (Saturday/Sunday-day/Sunday-evening) weekend move caps, its theta breakout impulse, its gamma-abs pull/pin/shock multipliers, and its Confirmed Scenario Gate (live/unclosed-candle damping) are intentionally deferred rather than transliterated line-for-line — see each function's own docstring in `forecast.py`.
  - **FlowImbalance damping, Zone Brake, and the Breakout Gate** — **Dankbit-original, not ported from Thales's source Pine script**, added per Thales dev feedback (a chat transcript reviewing the 18-candle forecast against a live BTC-4aug26 example, 2026-08-03, where the target direction was judged correct but the body's speed/confidence was judged overconfident given the underlying signal strength) — the first of several proposed fixes from that review, the rest deliberately deferred/scoped separately. **FlowImbalance** (`forecast.flow_imbalance(long_count, short_count)`) is `(Longs-Shorts)/(Longs+Shorts)` off the raw trade count for `current`'s own window (`dankbit.bands._compute_asset()`'s new `long_trade_count`/`short_trade_count`, a `direction == "buy"`/`"sell"` split of that same `trades` recordset, same convention `chart_png_zones`'s own "N longs / N shorts" annotation uses — extra return field, not persisted onto `dankbit.bands` itself, same pattern the 4 zero-crossing box-boundary fields already use; threaded onto `dankbit.forecast.snapshot` as 2 new `Integer` fields, default 0, read into `simulate_forecast`'s `current` dict via `to_dict()`) — when `|imbalance|` stays under `FLOW_IMBALANCE_NEUTRAL_THRESHOLD` (a near-equal Long/Short split, i.e. no real directional edge in who's actually trading), `body_confidence` is damped by `FLOW_IMBALANCE_BODY_DAMPING` (~20%, his own stated first fix) regardless of what the Greek levels themselves suggest. Computed once per call (step-invariant, like `consensus`); `None` (not 0.0) with no trade-count data at all (e.g. a snapshot row frozen before these fields existed), so the damping is skipped rather than reading "unknown" as "perfectly balanced". **Zone Brake** (`forecast._zone_brake_mult()`) shrinks `body_confidence` as the step's own pre-confidence net impulse (`raw_impulse_sum`, the same sum that used to feed `forecast_impulse` directly) points toward `top` (bullish) or `low` (bearish, mirrored — his own worked example only covered the resistance side) within `ZONE_BRAKE_ATR_DISTANCE` ATRs of that level — 1.0 (no brake) further out, floored at `ZONE_BRAKE_MIN_BODY_MULT` right up against it, so a genuinely strong signal can still produce some body there rather than flatlining completely; a distinct mechanism from the existing Gamma Neutral/Hysteresis Zone above, which brakes near `gamma_ref` (GAVG), not the Zone High/Low edges. **Breakout Gate** caps `projected_close` at `top`/`low` on an actual crossing attempt (`projected_open` starting on the near side) unless Gamma-Band Consensus's own `confirms_top`/`confirms_low` (a real top/low/gamma slope agreement over actual elapsed history, gated to the matching `consensus_direction`) AND Greek Flow's own directional `impulse` sign both agree — reusing these 2 already-computed, step-invariant signals rather than building a third confirmation mechanism from scratch (a lighter version of the fuller multi-condition gate his own review sketched, deliberately scoped down for this first pass). A candle already past the level isn't dragged back; the blocked excess bleeds into wick (`BREAKOUT_GATE_WICK_BLEED`, added onto `upper_wick`/`lower_wick` after their own `FORECAST_WICK_FACTOR`/`FORECAST_ATR_FACTOR` computation) rather than being discarded, so a rejected level still shows as tested rather than a flat ceiling. All 5 constants (`FLOW_IMBALANCE_NEUTRAL_THRESHOLD`/`FLOW_IMBALANCE_BODY_DAMPING`/`ZONE_BRAKE_ATR_DISTANCE`/`ZONE_BRAKE_MIN_BODY_MULT`/`BREAKOUT_GATE_WICK_BLEED`) are referenced directly in `simulate_forecast`'s own body, so — same as every other top-level tunable — they're `cfg`-overridable and exposed as per-asset (BTC/`eth_`-prefixed) `res.config.settings` fields (see Settings fields below).
  - **Greek Flow Engine** (`forecast.greek_flow()`) — **Dankbit-original, not ported from Thales's source Pine script**, unlike every engine in the cascade above. Motivated by the observation that every one of those engines reacts only to the *current* scan's static Greek levels/magnitudes; nothing asks whether a leg's own conviction is growing or draining scan-to-scan. Reads `current` against `history[-1]` — the OLDEST snapshot within the available window (up to `GREEK_FLOW_LOOKBACK_SNAPSHOTS`=3 prior rows, i.e. up to ~3 real hours back at `BUCKET_HOURS`=1, alongside `current` for 4 total points) rather than only ever the single most recent prior one — matching Thales's own live-dashboard reference implementation (`GreekFlowEngine`, sent directly by the indicator's original author), whose window diffs its first point against its last rather than a fixed 1-step lookback; a `coverage` term (`len(history)/GREEK_FLOW_LOOKBACK_SNAPSHOTS`, capped at 1) scales the resulting impulse down when fewer snapshots are available than that target, mirroring his own `cov` confidence term, so a still-filling window damps itself automatically rather than acting on a false 1-bucket-wide reading. `session_flow_mult`/`session_fakeout_mult` (from `session_activity_regime()`, see below — 1.0/1.0, a no-op, when no activity regime was computed) scale the flow impulse and the Fakeout Risk damping respectively, mirroring his own `SessionActivityRegimeEngine` feeding a `session_greek_flow_multiplier` into his `GreekFlowEngine.compute()`. 3 signals feed off `current` vs. that windowed `prev`: **Delta Flow** — rate of change of `bcd_abs`/`bpd_abs`/`scd_abs`/`spd_abs`, combined with the same bullish-positive sign convention `market_maker_gamma_contest` uses (buyer-side strengthening = bullish push, seller-side strengthening = pin/resistance building = opposing push) — feeds its own capped `impulse` term, additive alongside `vega_impulse`/`delta_impulse`/`mm_impulse`/etc. **Vega Flow** — same rate-of-change treatment for `*v_abs`, but mapped to `wick_mult`/`body_confidence_mult` instead of impulse, since vega has no inherent bullish/bearish direction (mirrors `vega_regime`'s own framing): growing buyer-side conviction expands wicks (accelerating expansion), growing seller-side conviction damps the body (accelerating compression). **Smart Liquidity Drift** — re-evaluates `smart_synthetic_liquidity()` on `history[0]`'s own Greeks (same `top`/`low`/`band_width`/`last_close` as the live call, deliberately reused rather than reconstructing that historical moment's own price context, so the diff isolates only the Greek levels/weights that actually moved) and adds a small impulse when a liquidity level is closing the gap to price; silent when a level is receding, since `liquidity_map_engine`'s own proximity-based decay already prices that in. **Fakeout Risk** — when Delta Flow's direction disagrees with the most recent real candle's own body direction, damps `body_confidence_mult` and expands `wick_mult` (same `GAMMA_BAND_CONFLICT_*`-style damping `gamma_band_consensus`'s own conflict case uses, scaled by `session_fakeout_mult`); agreement instead gives a small confirmation boost. Surfaces as `"Flow Fakeout"` in the candle's `mode` label. Inert (impulse 0.0, multipliers 1.0, `fakeout_risk` False) with no prior snapshot yet, same na-safe convention `liquidity_map_engine` uses for a blank liquidity column. Deliberately **not** `cfg`-overridable, following the same "top-level only" scoping rule as `vega_regime`/`market_maker_gamma_contest`/`smart_synthetic_liquidity`'s own internals — with one exception, see **Greek Flow Priority Hybrid** immediately below.
  - **Greek Flow Priority Hybrid** (`GREEK_FLOW_IMPULSE_WEIGHT`, `forecast_greek_flow_impulse_weight`, default **1.75**) — per a design discussion on whether Greek Flow could stand in for the rest of the cascade: the conclusion was that it should become the *primary* driver of the 4H candle's body direction/Close, without removing any structural engine (Smart Liquidity, Gamma Band, Curve Engine, Session Activity, Vega Regime) — those keep constraining how far a flow-driven move is actually allowed to travel before it gets absorbed into a wick instead of the body, rather than competing with Greek Flow as equally-weighted directional voices. Implemented as a single `simulate_forecast`-body-level multiplier on `greek_flow()`'s own `impulse` return value at the point it's summed into `forecast_impulse` alongside every other engine's impulse (`base_pull_impulse`/`gb_impulse`/`vega_impulse`/`delta_impulse`/`gamma_shock_impulse`/`mm_impulse`/`liquidity["impulse"]`/etc.) — `greek_flow()`'s own internal calibration constants (`GREEK_FLOW_DELTA_IMPULSE_STRENGTH` etc.) stay nested-helper-private and un-cfg-overridable as before; only this one call-site weight is new, and only it is cfg-overridable, since it's referenced directly in `simulate_forecast`'s own body (the same "top-level only" test used elsewhere) rather than being a nested-helper internal. Every other engine's impulse term, and every `body_confidence_mult`/`wick_mult` constraint in the cascade (Gamma-Band consensus/conflict, Cluster compression, Liquidity alignment, Session Activity, Vega compression, Fakeout Risk), is untouched — so a strong shock/consensus/liquidity signal can still override a weak or fake-out-flagged flow reading; this only changes Greek Flow's own relative weight in the additive sum. Defaults above 1.0 — unlike every other `*_WEIGHT`/`*_FACTOR` field in this section, which default to Thales's own as-ported baseline — specifically to make Greek Flow the dominant additive voice by default, reflecting that discussion's conclusion over the prior "one engine among many" weighting.

Thresholds/multipliers are fixed module constants, deliberately **not** `cfg`-overridable, same "top-level only" scoping rule as `vega_regime`/`market_maker_gamma_contest`/`smart_synthetic_liquidity`'s own internals.
  - **Gamma-Band Term-Structure Bias** (`forecast.gamma_band_term_slope()`) — **Dankbit-original, not ported from Thales's source Pine script**, since Thales's own rows only ever hold one expiry's worth of manually-entered levels at a time and so have no notion of a forward multi-expiry term structure at all. Added on user feedback that the forecast candles should visually track the same forward direction as the chart's own violet dashed **Gamma Band** line (`dankbit.bands.gamma_band`, see TradingView Chart Notes' Bands lines) — when that line is heading up toward the next tracked expiry, the forecast should trend up, and vice versa. `main.py`'s `_gamma_band_term_structure(asset)` reads the same persisted `dankbit_bands` rows/`dankbit_trade` expiration lookup `bands_json` serves, restricted to `expiration > NOW()` and to the 2 tracked instruments soonest to expire — exactly the two points forming that line's forward-most segment — and passes them into `simulate_forecast(..., gamma_band_term_structure=...)`. `gamma_band_term_slope()` turns the slope between those two points (normalized per `GAMMA_BAND_TERM_SLOPE_REF_HOURS`=24 real hours and by `band_width`, the same per-real-hour/band-width scale `gamma_band_consensus`'s own `slope()` uses, just a longer reference window since these two points are typically days apart rather than hours) into a direction (-1/0/1) and strength (0-1), dead-zoned/scaled by nested-helper-private `GAMMA_BAND_TERM_SLOPE_DEAD_ZONE`/`GAMMA_BAND_TERM_SLOPE_FULL_STRENGTH` (not `cfg`-overridable, same "top-level only" rule as `SLOPE_DEAD_ZONE`/`SLOPE_FULL_STRENGTH` inside `gamma_band_consensus`). Computed once per call (both points are step-invariant) and fed into `simulate_forecast`'s per-step loop as one more additive, step-decayed (`0.88 ** step`) impulse term — `term_direction * term_strength * GAMMA_BAND_TERM_SLOPE_IMPULSE_STRENGTH * combined_body_mult`, capped by `GAMMA_BAND_TERM_SLOPE_MAX_IMPULSE` — alongside, not overriding, every other engine's own impulse, so a strong shock/momentum/liquidity signal can still dominate a given step. `GAMMA_BAND_TERM_SLOPE_IMPULSE_STRENGTH`/`GAMMA_BAND_TERM_SLOPE_MAX_IMPULSE` (defaults 0.16/0.2) *are* top-level tunables (referenced directly in `simulate_forecast`'s own body), exposed as `forecast_gb_term_slope_impulse_strength`/`forecast_gb_term_slope_max_impulse`. Surfaces as `"Gamma Band Term Up"`/`"Gamma Band Term Down"` in the candle's `mode` label. Inert (direction 0, strength 0.0) with fewer than 2 forward-tracked-expiry `dankbit.bands` rows — e.g. right after this addon's first install, before `compute_snapshot()`'s hourly cron has tracked a 2nd expiry yet — same na-safe convention this engine's other history-dependent signals use.
  - **RSI Forecast Geometry** (`main.py`'s `_rsi_forecast_geometry()`, module-level function, not in `forecast.py`) — a purely retrospective, cosmetic-only adjustment applied to `/api/forecast/<asset>`'s response *after* `_compose_unified_forecast()` has already produced the full candle path: it can lengthen a rejection-side wick on the first few candles, but never touches Open/Close, so direction, body, path, and the EA1/EA2/EA3 anchor placements are unaffected. Computes RSI(14) and a 14-period MA of RSI off the selected timeframe's own closed candles (`Trade.get_candles(asset, interval=timeframe, limit=260)`); when `|RSI − RSI MA|` exceeds a 5-point dead zone, `gap_strength` (0-1, saturating at a 15-point gap) sets a rejection-wick budget capped at `0.20 * ATR` of that timeframe, tapering linearly across the affected candles (6 on 1H, 3 on 4H, 1 on 1D) and applied to `high` (RSI below its MA — bearish-exhaustion/upside-correction risk) or `low` (RSI above its MA — bullish-exhaustion/downside-correction risk) only. That effect is damped up to 90% by a **closed-1H momentum persistence** score (`momentum`, 0-1) — a blend of cumulative 8-candle move vs. ATR, body-direction dominance, close-location-within-range, and EMA20 slope, all evaluated in the *opposite* direction to the RSI correction — so a strong, still-intact trend suppresses the correction wick almost entirely rather than fighting it. Recomputed fresh on every request (no persistence, no `cfg` overrides — not one of the `res.config.settings` Thales Forecast tunables); wrapped in its own `try`/`except` in `forecast_json` so a failure serves the untouched Forecast path rather than 500ing, surfaced via the response's new `rsi_context` field (`{available, rsi, rsi_ma, gap, gap_strength, momentum_1h, effective_geometry_weight, affected_candles}`, `{"available": False}` when there isn't enough closed-candle history yet or on error).
- No color-key footer legend; each line/series still carries its own identifying `title`.
- Footer status shows: `<weekly-expiry>  ·  <monthly-expiry>  ·  N trades  ·  Nearest: <expiry>  ·  Option Flow: Auto → <N>h/<N>d trailing window (only while Option Flow = "Auto (Time to Expiry)")  ·  Last trade: <UTC timestamp>`; trade count is `active_trade_count` from `/api/last-trade/<asset>` (a `search_count` of that asset's active, not-yet-expired instruments' trades) when the "Gamma Horizon" checkbox is off, or the `/api/gamma-horizon/<asset>` response's own `trade_count` when it's on (`refreshLastTrade()` only sets the count from `active_trade_count` while `!SHOW_GAMMA_HORIZON`, so `refreshGammaHorizon()` owns it otherwise). The `Nearest:` segment is the same nearest-active-expiry the yellow zones boxes use (`dankbit.bands.nearest_expiry()`, a cheap standalone `SELECT DISTINCT expiration ... LIMIT 1` lookup, no curve-building) — shown regardless of timeframe (`refreshNearestExpiry()`, a lightweight standalone lookup unlike the boxes' own full computation — though both are now shown on every timeframe), via a shared `updateStatusLine()` that it, `refreshGammaHorizon()`, `refreshLastTrade()`, and `refreshZonesBoxes()` all call so none overwrites another's own slice of the status text. The `Option Flow: Auto → <N>h/<N>d trailing window` segment shows only while the Option Flow dropdown is on "Auto (Time to Expiry)" — `refreshZonesBoxes()` sets `zonesBoxAutoHours` from `/api/zones-box/<asset>`'s echoed `window_hours` (the `_auto_window_hours()`-resolved value, see TradingView Chart Notes' Option Flow dropdown), cleared to `null` (segment hidden) by every non-auto mode and by `clearZonesBoxes()`; `zonesBoxHoursLabel()` applies the same `>=24 && %24==0 → Nd else Nh` split `/4l/<asset>`'s own `hoursLabel()` uses. `Last trade:` is `dankbit.trade.get_last_trade(asset)`'s own `deribit_ts` (`/api/last-trade/<asset>`, `last_trade_json` — same cheap-standalone-lookup, no-curve-building pattern as `/api/nearest-expiry/<asset>`), asset-wide via `get_last_trade()`'s plain `ilike` match rather than restricted to any one expiry/instrument, formatted in genuine UTC (not the chart's own browser-local `tzOffset` shift, since this is a staleness check against server time, not a chart-axis position) — added so a stalled `dankbit_ws` ingestion service (its DB connection can die without crashing the container, silently dropping every trade — see `dankbit_ws_service/dankbit_ws_batch.py`) shows up as a growing gap between this timestamp and "now" at a glance, without checking container logs or querying the DB directly. Omitted from the footer entirely if the asset has no trades at all (`last_trade_ts: null`).

## Odoo Addon (`my_addons/dankbit/`)

The addon depends only on `website`. Key components:

**Models:**
- `dankbit.trade` — Core model. Fields map directly to Deribit trade fields. `strike` and `option_type` are computed from `name` (instrument name like `BTC-29NOV24-98000-P`). `days_to_expiry` is UTC-safe. `get_hours_to_expiry()` returns continuous time used in Black-Scholes. `get_open_interest_by_currency(asset)` returns `{instrument_name: open_interest}` for every option instrument on `asset`, from Deribit's public `get_book_summary_by_currency` — one cached bulk call per currency (`_DERIBIT_CACHE`/`deribit_cache_ttl`, see Caching below), not a per-instrument lookup. `get_index_price(instrument)` — the live "current price" reference (chart marker lines, `dankbit.bands`'s `role_close`, the Thales Forecast engine's `projected_open`), moved to **Binance spot** (`/api/v3/ticker/price`) per product decision, same as `get_candles()` below — kept on the same `deribit_timeout`/`deribit_cache_ttl` settings (not renamed, still just "how long to trust a cached public-API price") but cached in `_BINANCE_CACHE` now, not `_DERIBIT_CACHE`, since it's no longer a Deribit call. Confirmed **not** to feed the Black-Scholes Greek curves themselves (`delta.portfolio_delta`/`gamma.portfolio_gamma`/etc. evaluate across the configured `STs` price grid using each trade's own strike/IV/expiry, never this value as `S`) — the one exception is `forecast.trade_weighted_per_leg_greeks()` (behind the off-by-default `forecast_trade_weighted_greeks` toggle, see below), which evaluates each trade's per-contract greek at this price directly, mirroring Thales's own live-price-based design. `get_candles(asset, interval="4h", limit=500)` — real **Binance spot** candles, oldest-first, native 1h/4h/1d resolutions, no aggregation needed (moved off Deribit perpetual futures per product decision — see TradingView Chart Notes for the full rationale/what stayed on Deribit). Cached server-side (`_BINANCE_CACHE`/`_BINANCE_CANDLES_CACHE_TTL`=5s, separate from `_DERIBIT_CACHE` since this isn't a Deribit call). Moved here from `ChartController._fetch_candles` (a plain public REST lookup with no HTTP-request dependency, the same category of call as `get_index_price`/`get_open_interest_by_currency` above) so `dankbit.forecast.snapshot.get_forecast_points()` — and thus both `/api/forecast/<asset>` and `dankbit.forecast.log`'s cron — can fetch real historical bars without needing a request context. Shared by `klines_proxy` (which just reverses the result to newest-first for the frontend) and `get_forecast_points`.
- `dankbit.bands` — **One record per instrument** (e.g. `"BTC-10JUL26"`, unique-constrained on `instrument`), not per snapshot-in-time — a row's position on the TradingView chart is still that instrument's own expiration time, looked up from `dankbit_trade.expiration` when the API serves it (see below and TradingView Chart Notes' Bands lines), never `computed_at` below. Fields: `computed_at` (Datetime, `default=fields.Datetime.now` — backend visibility only, e.g. "how stale is this row"; refreshed to the moment `_compute_asset()` ran on every `_persist_extrema()` upsert, not just set once at creation), `asset`, `instrument`, `index_price`, `high_resistance`/`low_support` (the highest/lowest price where the Longs-vs-Shorts payoff curves cross each other — not where either crosses zero, and **not** relative to `index_price`; same `longs.payoffs - shorts.payoffs` sign-change `build_zone_curves()` finds internally for its own ±$2000 auto-zoom), `high_resistance_positive`/`low_support_positive` (Boolean — whether the *payoff value* at that intersection, not its price, sits above or below the zero-payoff line; interpolated via `np.interp` at the crossing price against `longs_obj.payoffs`, which equals `shorts_obj.payoffs` at a true crossing — drives the `+`/`-` marker on the TradingView chart, see TradingView Chart Notes), `gamma_band` (average of 4 gamma extrema — Buyer Call Gamma (BCG), Buyer Put Gamma (BPG), Seller Call Gamma (SCG), Seller Put Gamma (SPG) — the same numbers the `/<instrument>/zones` PNG page's info overlay shows, sourced from `options.per_leg_greeks()` against this same instrument's `trades`/`STs`; averaged via the module-level `_avg_present(*values)` helper, not a fixed `/4.0` — it averages only the non-zero elements it's given and returns `0.0` if none are, so a leg with no trades in the window (`options.per_leg_greeks()` itself reports that leg's price as `None`; `forecast_lib.per_leg_greeks()` — the wrapper this model actually calls — collapses that `None` to `0.0` before it reaches `_avg_present()`, see `options.py` below) is excluded from the average instead of dragging it toward 0), `delta_band` (same `_avg_present()` treatment over the 4 delta-saturation prices, one per leg, also from `options.per_leg_greeks()` — not derived from gamma, since portfolio delta and portfolio gamma are numerically related but conceptually distinct measures here), `smart_liq_upper_price`/`smart_liq_lower_price` (Thales's newer-version Smart Role-Aware Synthetic Liquidity levels — `forecast.smart_synthetic_liquidity()`, the same upper/lower levels the Thales Forecast candle engine already uses internally via `liquidity_map_engine` — computed against this same instrument's own `high_zone_max`/`low_zone_min` band, per-leg `legs` dict, and `index_price`, so this model's values can never disagree with what that engine sees; `0.0` means absent — either a degenerate `high_zone_max<=low_zone_min` band, or that side's blend had no contributing legs, see `smart_synthetic_liquidity`/`weighted_avg2` — same `0.0` = absent convention `high_zone_min`/`max` etc. already use on this model, not `None`), `smart_liq_upper_strength`/`smart_liq_lower_strength` (that same `smart_synthetic_liquidity()` call's own `upper_liq_m`/`lower_liq_m` — which side is the *stronger*/more dominant liquidity level, not just where it sits; drives the TradingView chart's per-point Smart Liquidity marker emphasis, see TradingView Chart Notes; same `0.0` = absent convention as the price fields), `high_zone_min`/`high_zone_max`, `low_zone_min`/`low_zone_max`, `middle_zone_min`/`middle_zone_max` (same definitions as `options.zone_summary()`'s `high_zone`/`low_zone`/`middle_zone` — see Zones chart above and `options.py` below — stored as a `_min`/`_max` Float pair per zone since a single Float can't hold a range; `high_zone`/`low_zone` default `0.0`/`0.0` when neither curve ever crosses zero, same convention `high_resistance`/`low_support` use, while `middle_zone` is always defined), `seller_max_profit`/`buyer_max_loss` (see `dankbit.forecast.snapshot`'s `bml`/`smp` fields — price where the Shorts payoff curve peaks / where the Longs curve bottoms out, against this same `longs_obj`/`shorts_obj`; same values `options.zone_summary()`'s `seller_max_profit`/`buyer_max_loss` show on the `/<instrument>/zones` PNG page's info overlay, not exposed via `/api/bands/<asset>` — model-only, feeds the `/api/zones-box/<asset>` teal box instead, see TradingView Chart Notes), and the 32 individual per-leg gamma/delta/theta/vega price + Abs fields (`bcg_price`/`bcg_abs`/`bpg_price`/`bpg_abs`/`scg_price`/`scg_abs`/`spg_price`/`spg_abs`, and the BCD/BPD/SCD/SPD, BCT/BPT/SCT/SPT, BCV/BPV/SCV/SPV equivalents — see `_PER_LEG_GREEK_FIELDS`) behind `gamma_band`/`delta_band`'s averages — the exact same numbers, same field names, and same scaling (`*_abs` is `abs(value)/scale` — 1e6 gamma, 10 delta, 1e4 theta, 100 vega — matching the `/<instrument>/zones` PNG page's own Abs. lines, not rounded further) as `dankbit.forecast.snapshot`'s own `bcg_price`/`bcg_abs`/etc. fields, sourced from the same `forecast_lib.per_leg_greeks()` this model calls directly — this model, the `/<instrument>/zones` PNG page, and the Thales Forecast engine can never quietly disagree on any of these 32 numbers for the same trades, all three ultimately calling the same `options.per_leg_greeks()`. Also carries the **zone confirmation** fields backing the gating pipeline below: `zones_confirmed_at` (Datetime — when the persisted High/Low/Middle zones last passed the session/quality gate, or the emergency two-scan override), `zones_confirmation_reason` (Char — e.g. `"session:London Mature"`, `"session:NY/London Overlap"`, or `"emergency:<reason>:two-hour-confirmed"`), `zone_candidate_at` (Datetime — the most recent hourly out-of-session "candidate" zone scan, staged but not yet confirmed), `zone_candidate_hits` (Integer, default `0` — consecutive count of mutually-consistent hourly candidate scans; needs ≥2 to trigger the emergency override), and 8 `candidate_*` Float fields mirroring the confirmed zone/SMP/BML fields (`candidate_high_zone_min`/`_max`, `candidate_low_zone_min`/`_max`, `candidate_middle_zone_min`/`_max`, `candidate_seller_max_profit`, `candidate_buyer_max_loss`) that stage a not-yet-confirmed reading without disturbing the last confirmed one — all 8 reset to `0.0` on every confirmed upsert (see `_persist_extrema` below). `_compute_asset(asset, expiry_index=0, hours=None, future_days_only=False)` is the shared computation core (the `expiry_index`-th soonest active expiry — 0 is nearest, 1 is the one after that, via a raw `SELECT DISTINCT expiration` query, `_distinct_expirations(asset, as_of, limit, future_days_only=False)`, so a single expiry's 100k+ trades can't crowd out the next one; `future_days_only=True` (passed straight through from `_compute_asset`) rounds the query's lower bound down to UTC midnight **plus one day**, excluding today's still-open expiry so E1/E2/E3 anchor on tomorrow/day-2/day-3 instead of a contract that hasn't settled yet — used by the multi-expiry forecast engines (see `dankbit.forecast.snapshot`/`dankbit.forecast.next_candle` below), not by the Bands/Zones confirmation pipeline, which keeps the plain nearest-expiry-including-today behavior — trades since 00:00 UTC through now for that expiry by default, or the trailing `hours` hours through now when given — see `get_box`'s `hours` override below, `options.build_zone_curves()`, then `forecast_lib.per_leg_greeks()` for the 32 per-leg fields (`gamma_band`/`delta_band` are simply the average of 4 of those), `high_zone_min`/`high_zone_max`/`low_zone_min`/`low_zone_max` built from the same `short_crossings`/`long_crossings` also used for the 4 raw zero-crossing box boundaries (rather than calling `options.zone_summary()` again and re-finding the same crossings), `middle_zone_min`/`middle_zone_max` from `seller_max_profit`/`buyer_max_loss`, then `high_resistance`/`low_support`/`seller_max_profit`/`buyer_max_loss`, that expiry's own `instrument` string and `expiration` datetime, plus 4 zero-crossing box boundaries — each curve's own highest/lowest zero-crossing, also not relative to `index_price` (same principle as `high_resistance`/`low_support`; see below) — plus `long_trade_count`/`short_trade_count` (a `direction == "buy"`/`"sell"` split of that same `trades` recordset, same convention `chart_png_zones`'s own "N longs / N shorts" annotation uses) feeding `forecast.flow_imbalance()` (see the Thales Forecast candles section's FlowImbalance/Zone Brake/Breakout Gate bullet) — like the 4 box boundaries, an extra return field, never persisted onto this model — returns `None` if there's nothing computable (missing index price/expiry at that index/since-midnight trades) rather than writing a row that would silently look like real data (e.g. the configured price-range floor). Persisted as a side effect of `get_box_n()` (below), whose **only** caller, for every tracked `expiry_index` including 0, is the hourly cron, `compute_snapshot()` — there is still no browser-triggered path that persists here. Unlike the original design, though, `compute_snapshot()` no longer persists every raw `_compute_asset()` reading unconditionally: a **zone confirmation / gating pipeline** (new methods below — `_band_confirmation_session`, `_band_quality_gate`, `_zone_quality_gate`, `_zone_structural_change_gate`, `_stage_zone_candidate`, `_gamma_quality_gate`, `_persist_live_gamma`) decides, on every hourly tick, whether that tick's reading is trustworthy enough to become the new confirmed structural row, gets staged as an unconfirmed "candidate" instead, or (independently) is at least allowed to refresh the live Gamma Band alone. `/api/zones-box/<asset>` and `/api/bands/<asset>` also gained an optional `?hours=` trailing-window **live preview** mode (1–168h, clamped) that recomputes fresh via `_compute_asset(..., hours=hours)` without ever writing to this model — see `get_box`/`get_box_n` below and the Controllers section's `bands_json`/`zones_box_json`.

  **Zone confirmation / gating pipeline** — added because unconditionally persisting every hourly raw computation let a single noisy/thin-trading hour redraw the yellow/teal zones boxes and the Bands lines with a structurally different reading, even though those are meant to read as slow-moving reference levels. The fix restricts *structural* changes (the 4 zero-crossing box boundaries, the 3 zone min/max pairs, SMP/BML, High/Resistance-Low/Support) to two daily "mature" session windows, while still letting the live Gamma Band (and only the Gamma Band) refresh every hour regardless of session, and giving a genuinely large structural move outside those windows a fast (2-hour) emergency path instead of waiting up to a full day for the next session.
  - **`BAND_CONFIRMATION_WINDOWS_UTC`** — module constant, `((8, 30, 10, 30, "London Mature"), (14, 0, 15, 30, "NY/London Overlap"))`: two UTC windows during which structural confirmation may happen at all. Midnight UTC is deliberately excluded (thin liquidity, unreliable levels).
  - **`_band_confirmation_session(when_utc=None)`** — returns the session name (e.g. `"London Mature"`) if `when_utc` (default: now) falls inside one of `BAND_CONFIRMATION_WINDOWS_UTC`, else `None`.
  - **`_band_quality_gate(data)`** — `(bool, reason)`. Rejects a raw `_compute_asset()` reading when `index_price`/`high_resistance`/`low_support` is missing or collapsed (`high <= low`, reason `"missing-or-collapsed-intersections"`); when the trade sample is too thin — `dankbit.band_min_total_trades_{btc,eth}` (default **80**/**40**) total trades or `dankbit.band_min_side_trades_{btc,eth}` (default **10**/**5**) on either the long or short side, reason `"insufficient-long-short-sample"`; when the band width is under `dankbit.band_min_width_pct` (default **0.015**) of index price, reason `"band-width-below-minimum"`; or when every one of the 16 per-leg `*_abs` fields sums to zero abs strength, reason `"no-greek-strength"`. `(True, "confirmed")` otherwise. These 5 thresholds are read via `ir.config_parameter` (`icp.get_param(key, default=...)`), not exposed as `res.config.settings` UI fields.
  - **`_zone_quality_gate(data)`** — `(bool, reason)`. First requires `_band_quality_gate` to pass, then additionally requires: all 4 raw zero-crossing box boundaries `> 0`; all 6 zone min/max values plus `index_price` present and non-inverted; the Low zone's max below the High zone's min (no overlap); the Middle zone nested inside the outer two; each of the High/Low zone widths within `dankbit.zone_max_width_pct` (default **0.03**) of index price; and the independently-computed `high_resistance`/`low_support` sitting within `dankbit.zone_band_proximity_pct` (default **0.003**, tolerance-padded) of the corresponding zone boundary — a sanity cross-check that the box-boundary computation and the Longs-vs-Shorts intersection computation still agree with each other.
  - **`_zone_structural_change_gate(record, data)`** — `(bool, reason)`, used only outside a confirmation session. Compares a fresh raw reading against `record`'s last **confirmed** baseline (returns `False` if there is no confirmed baseline yet) and flags a material change — via `_zone_center(data, prefix)` (the midpoint of a zone's own `_min`/`_max`) — when: any of the High/Low/Middle zone centers shifted beyond `dankbit.zone_emergency_outer_shift_pct`/`dankbit.zone_emergency_middle_shift_pct` (default **0.006**/**0.004**) of index price; any zone's width ratio (old vs. new, floored at `max(index_price*0.00025, 1.0)`) reaches `dankbit.zone_emergency_width_ratio` (default **1.75**) — a "regime change" in how wide the zone is, not just where it sits; or price has traded convincingly beyond the confirmed zone plus `dankbit.zone_emergency_breakout_buffer_pct` (default **0.002**) with the center itself also having migrated. Reason strings identify which check tripped (e.g. `"upper-zone-center-shift"`, `"lower-zone-width-regime-change"`, `"price-accepted-above-confirmed-zone"`); `(False, "no-material-zone-change")` otherwise.
  - **`_stage_zone_candidate(record, data)`** — writes the current raw reading into the 8 `candidate_*` fields on `record` and returns the new `zone_candidate_hits` count: incremented from the prior value when this candidate's 3 zone centers all sit within `dankbit.zone_candidate_similarity_pct` (default **0.0025**) of index price of the *previous* candidate (i.e. two consecutive hourly scans agree), reset to `1` otherwise.
  - **`_gamma_quality_gate(data)`** — `(bool, reason)`, a deliberately lighter gate than `_band_quality_gate` so the live Gamma Band can update on its own cadence independent of structural confirmation. Rejects when `gamma_band` is falsy/`0` (`"missing-gamma-band"`); when total trade count is under `dankbit.gamma_live_min_total_trades_{btc,eth}` (default **40**/**20**, `"insufficient-gamma-sample"`); or when the summed abs of the 4 gamma-leg `*_abs` fields is under `dankbit.gamma_live_min_abs_{btc,eth}` (default **0.0001**, `"no-live-gamma-strength"`).
  - **`_persist_live_gamma(data)`** — writes only `computed_at`/`index_price`/`gamma_band` and the 8 gamma-leg fields (`bcg_price`/`bcg_abs`/`bpg_price`/`bpg_abs`/`scg_price`/`scg_abs`/`spg_price`/`spg_abs`) onto an **existing** row for `data["instrument"]`; never creates a row and never touches the structural High/Low/Middle zone or SMP/BML fields. No-op (logs, returns `False`) if no row exists yet for that instrument.
- `dankbit.live.band` — **no longer data-collection-only**: `/api/live-band/<asset>` (`live_band_json`, new — see Controllers) now reads it directly, feeding the TradingView chart's Smart Liquidity dominance-dot rendering (`refreshLiveBandDots()`, see TradingView Chart Notes) — previously this model had genuinely no route/chart/checkbox reading it anywhere (a standalone `/z/<asset>` chart and a Delta Chart "Live Bands" checkbox that used to read it were both removed, and the model/cron were kept purely to keep accumulating history for possible future use; that future use has now arrived). - `dankbit.signal` (`models/signal_bot.py`, `_description = "Thales Signal Bot"`) — the **Thales Signal Bot**: an hourly, append-only automated forward-test that decides, records, and later grades one auditable BTC/ETH trade decision per hour, entirely independent of any manual chart interaction (no browser action ever writes here — only its own two crons do). Core design principle (module docstring, reworded — see Direction gate below for the current mechanics): **Daily macro/tactical and 4H price trends own direction** — Forecast (E1/E2/E3 anchor candles), moving Greek concentration, and 1H option-structure (RTM zones) grade/confirm the setup or time the entry, never reverse the direction call; every row is create-only (no later revision ever rewrites a past decision, so accuracy stats can't be quietly retconned). One row per `(asset, evaluated_at)` (hour-truncated), the `evaluate()` cron's own `search_count` pre-check (not a DB unique constraint) skipping a re-run within the same hour rather than erroring. Fields: `asset`, `evaluated_at`/`utc_day`, `kind` (`official`/`shadow`/`no_trade` — set once at creation, never mutated afterward), `state` (`watch`/`armed`/`active`/`tp`/`sl`/`expired`/`cancelled`/`missed`/`ambiguous`/`rejected` — `cancelled` is reachable only via manual admin edit in the backend form, never set by either cron;   **`_market_trend(candles, profile="tactical")`** — reworked from a single fixed EMA20/EMA50 read into a `profile`-parameterized classifier, since Daily Macro, Daily Tactical, 4H, and 1H each need their own lookback/EMA-window balance rather than sharing one. Each profile sets its own `(minimum_closed_candles, fast_ema_period, slow_ema_period, slope_lookback)`: `daily_macro` (210/50/200/20 — the long-horizon bias, requires 320 requested daily candles), `daily_tactical` (60/20/50/8 — a faster read over just the trailing 100 daily candles), `4h` (210/20/50/8, plus its own EMA200 check against `ema_slow`), `1h` (80/20/50/6), and the fallback `tactical` (55/20/50/5, the original single-profile behavior, still used by `_breakout_retest_setup`-adjacent callers that don't specify a profile). Score composition also varies by profile: `daily_macro` weighs `close > EMA(slow)` + `EMA(fast) > EMA(slow)` at 30 each and `EMA(fast)` rising at 20, `4h` adds its own `EMA(slow) > EMA(200)` check at 15, everything else follows the original close/EMA(fast)-slope/EMA(fast)-vs-EMA(slow) 25/20/20 split — each profile then adds its own `structure_weight` (20/30/35) for the confirmed-swing-structure agreement bonus/penalty.   **Direction gate — reworked from "Daily AND 4H must both agree" to "4H leads, Daily can only veto":** `standard_direction = "long"` when `trend_4h == "up"` **and neither** `trend_score_daily` **nor** `trend_score_daily_tactical` is below `-60` (i.e. Daily Macro/Tactical isn't *strongly* opposed); mirrored for `"short"` (`trend_4h == "down"` and neither Daily score exceeds `+60`); `"neutral"` otherwise. This replaces the old strict `trend_daily == trend_4h` equality — a neutral or mildly-opposing Daily read no longer blocks a clean 4H trend, only a strongly opposing one does. `final` score = `direction_sign * (0.20*trend_score_daily + 0.10*trend_score_daily_tactical + 0.30*trend_score_4h + 0.20*score4 + 0.15*gamma_score + 0.05*greek_score) * (quality/100)` (reweighted from the old 0.25/0.30/0.20/0.15/0.10 split to make room for the new Daily Tactical term, trimming Greek-direction's own weight), where `score4` is `_anchor_score()`'s own E1/E2/E3-weighted (0.45/0.35/0.20) 4H forecast-candle-body direction score and `quality` (`_quality()`) is anchor/snapshot coverage × average anchor confidence, damped 12% in a low-activity regime and 10% on weekends. A long list of `reasons` gates are still evaluated regardless of direction (coverage, quality, trend/forecast/Greek alignment thresholds, a 1H-forecast-pullback allowance that only blocks on a *strongly opposing* 1H projection, not a merely counter-trend 1H market), but — unlike before — a populated `reasons` list before the RTM stage no longer forces `thales_eligible=False` by itself; see `thales_eligible`/`thales_official_filters` below for the current split.

  **`thales_eligible` / `thales_official_filters` split** — `thales_eligible` was loosened twice now: first to require only `standard_direction != "neutral"`, `entry > 0`, and a valid structural trade plan (`swing_level`/`stop`/`target` all set, `rr >= 2.0`) instead of the full `reasons` list being empty; then loosened further, dropping the structural-plan requirement too — `thales_eligible` now requires only `standard_direction != "neutral"` and `market_price > 0` (the live index price, captured before `entry` gets reassigned to the RTM zone's own proximal edge — see Entry timing below). The structural-plan check (`stop and target and rr >= 2.0`) moved onto `rtm_official_eligible` itself instead, alongside its own RTM conditions — so a setup can now be `armed`/watched with no confirmed stop/target at all, only losing Official eligibility until one exists. The stricter checks that used to gate eligibility outright (anchor coverage ≥3 on both 4H/1H, `quality >= min_quality`, `final >= 35.0`, and each of score4/scored/gamma/greek/score1 clearing its own alignment threshold) still live in the separate `thales_official_filters` bool, which gates **Official** promotion only (`rtm_official_eligible` requires `thales_official_filters`, not bare `thales_eligible`). Net effect: **price structure alone is enough to surface a Watch/Armed setup on the panel**; Forecast/Greeks/option-data quality, and now the structural stop/target itself, can still block Official, but can no longer hide a directionally valid setup entirely.

  **`rtm_watch` / `entry_model = "ftb_watch"`** — new: `rtm_watch = thales_eligible and rtm_zone and rtm_path_clear` (a valid RTM zone with a clear path to target, regardless of touch count or entry-trigger confirmation) now feeds `shadow_candidate` alongside `official_eligible`/`reclaim_shadow`/`later_touch_shadow`/`breakout_shadow`, and resolves to `entry_model="ftb_watch"` when none of the more-confirmed entry models apply — surfacing a "setup detected, not yet triggered" state (panel title `"ARMED <DIRECTION>"`) that previously stayed invisible until either a reclaim or a full FTB confirmation.

  **Breakout-Retest options gate loosened** — `breakout_options_aligned`'s old hard AND-gate (gamma/greek/score4 each individually ≥ its own threshold, required for the setup to be a `breakout_candidate` at all) was replaced with a blended `breakout_option_composite = breakout_sign * (0.40*gamma_score + 0.35*greek_score + 0.25*score4)`, which only matters via `breakout_options_strongly_opposed = breakout_option_composite <= -35.0` — now purely an **Official-only** block (appended to `breakout_official_eligible`'s own condition, with its own `reason` line: `"Options composite strongly opposes the break: Official is blocked, Watch/Shadow remains visible"`). `breakout_candidate` itself now only requires `daily_not_opposed` (using the same ±60 Daily-veto thresholds as the Direction gate above) — a `breakout_watch`/shadow setup is no longer hidden by weak or opposing options confirmation, only Official is.

  **`_latest_anchors(asset, timeframe, now_naive)`** — the latest not-yet-future `dankbit.forecast.next_candle` revision for each of E1/E2/E3 (within an 8h lookback), skipping any expiry whose `snapshot_id` fails `_snapshot_complete()` (same 4-leg gamma/delta/theta/vega price+abs completeness rule as `main.py`'s `_forecast_leg_completeness()`/`forecast_next_candle.py`'s inline `data_complete` check on `preview_for_dashboard()` — three independent implementations of the identical rule across this addon). `_latest_snapshots(asset, now_naive)` does the analogous lookup against `dankbit.forecast.snapshot` (3h lookback), same completeness gate. **`_market_trend(candles)`** — the Daily/4H/1H trend classifier: drops the still-forming last candle, then scores (clamped ±100) from EMA20-vs-price, EMA20-vs-its-own-value-5-bars-ago (slope), EMA20-vs-EMA50, and a 5-candle-fractal swing-structure check (higher-highs+higher-lows / lower-highs+lower-lows on the 2 most recent confirmed swings), classified `up`/`down` at a ±40 threshold else `neutral` — needs ≥55 closed candles or returns neutral/0. **`_option_direction_scores(asset, now_naive)`** — direction of each Greek's dollar-weighted price *centre* moving between the oldest and newest complete same-expiry `dankbit.forecast.snapshot` row in an 8h window (not an absolute level — genuinely a rate-of-change signal), a 0.5%-of-index-price centre shift mapping to a full ±100 score; Gamma carries 50% of the blended `combined` score, Delta 25%, Vega 15%, Theta 10%.

  **Entry timing, gated behind `thales_eligible`:** `_structural_stop(direction, entry, candles_4h)` finds the latest CONFIRMED 4H swing (same 5-candle-fractal detector as `_market_trend`, scanned backward for the most recent swing beyond `entry`) and places the stop beyond it with an ATR-scaled buffer + minimum-risk floor. `_levels(direction, entry, stop, snapshots, rows4)` picks the target from confirmed structural levels (the 3 tracked snapshots' own `top`/`low`/`bml`/`smp` plus the 3 anchor candles' `forecast_high`/`forecast_low`/`forecast_close`) — requires RR≥2.0, prefers the farthest candidate still inside a 2R–4R "sweet spot", else falls back to the nearest RR≥2 candidate. `evaluate()` always runs this pair unconditionally, off `entry = market_price`, whenever `direction != "neutral"` — this is the baseline stop/target the panel shows before (or absent) any RTM zone; it's what a Breakout-Retest setup keeps using directly (see below), and it's also `swing_level`'s only source. `_entry_reference_levels(asset, direction, snapshots)` collects CONFIRMED (never candidate/unconfirmed) Zone/Band/Smart-Liquidity levels from the persisted `dankbit.bands` rows matching the same expiry instruments the snapshots already accepted, falling back to the snapshot's own frozen `top`/`low` only if no Bands row exists yet for that instrument.

  **`_rtm_zone_candidates(direction, candles_1h, reference_levels)`** — a Signal-Bot-local "Reversal-to-Mean" supply/demand base detector (RBR/DBR/DBD/RBD structures — explicitly does not alter or feed back into Thales's own Zones), scanning up to 70 trailing closed 1H candles for 1–5-candle consolidation bases (widened from 1–3) with a real incoming move before and a real departure impulse after. `reference_levels` (Zone/Band/Smart-Liquidity confluence) is now optional — `reference_levels or []`, and overlapping one is no longer a hard requirement to keep a base at all, only a scoring bonus (`confluences`) and a `nested` flag (≥2 distinct source groups) — a genuine price-action Base with no confluence still surfaces. Each base candidate must now also look like a real doji/small-body consolidation, not just a tight range: every candle's own body share of its high-low range must be ≤0.45 (max) and ≤0.32 (average), and for a multi-candle base, all but one adjacent pair must overlap in high/low range. Scored 0–100 from departure strength (`departure_score`, up to 25 plus a directional-body bonus, up from 15), base tightness (`base_score`, 12 vs 7 depending on width/body-share), freshness (`freshness_score`: 18 for a genuine zero-touch base, 12/4/0 for 1/2/3+ touches — `fresh` itself is now `touches == 0`, was `<= 1`), multi-source confluence ("nested", +15), distance already traveled, pre-touch compression, and a departure gap — base constant lowered from 20 to 12 to make room for the larger departure/freshness weights. New per-zone fields: `departure_atr` (impulse ÷ ATR) and `zone_definition: "full_wick_range"` (this detector's zone is always the base's complete wick-to-wick envelope, never a body-only range — see the Breakout-Retest linkage below).

  **`_select_rtm_zone(direction, entry, zones, atr_4h)`** picks the best in-range zone — eligibility requires the zone to sit on the correct side of `entry` (`zone["low"] <= entry` for long, `zone["high"] >= entry` for short), within `max_distance` of it, and `touch_count <= 2` (a base touched 3+ times is no longer considered fresh enough to trade). Ranking is now **distance-penalized** rather than a flat score-plus-structure-bonus pick: `distance_to_market = abs(entry - proximal)` is computed per candidate and the sort key becomes `score + 5.0*(structure_priority - 1) - 18.0*distance_to_market/distance_unit` (`distance_unit = max(atr_4h, 0.003*entry)`, `formed_at` as the tiebreak) — so an excellent but remote Base (small DBR/RBD still keep their own +5 structural nudge, since they mark the pullback's own end) can no longer displace the nearest credible entry zone and turn its own proximal line into a mere stop reference.

  **RTM-zone-anchored entry/stop/target, superseding the `_structural_stop`/`_levels` baseline.** Under `thales_eligible`, both directions' raw RTM bases are built and `_select_rtm_zone(direction, market_price, rtm_zones, atr_4h)` is called against the **live index price** (`market_price`, captured before `entry` is touched) rather than the baseline `entry`. No zone found leaves `entry`/`stop`/`target` at the `_structural_stop`/`_levels` baseline and appends `"Thales setup armed: waiting for a credible 1H RTM zone"`. Once a zone is found, entry timing takes over completely: `entry` is reassigned to the zone's own proximal edge (`entry_zone_high`/`low` for long/short); the invalidation level is built off the zone's *distal* edge plus a buffer (`stop_buffer = max(0.10*ATR1H, 0.15*zone_width, 0.0005*entry)`), widened further out if `swing_level` (the earlier 4H-swing-based stop) sits even farther beyond the zone (`max(distal, swing_level or distal) + buffer` short-side, mirrored for long) — so the 4H swing still acts as a floor on stop distance, just no longer as the stop's own direct source; `_levels()` is then called a second time with this new entry/stop pair to recompute `target`/`rr`, appending `"RTM Entry/Distal Stop found, but no structure-backed target offers minimum 2R"` if it still can't clear 2R. `trigger_basis` for an RTM-anchored setup reads `"1H RTM <STRUCTURE> <TYPE> proximal"` (was the shorter `"RTM <TYPE> FTB"`). `_entry_trigger(direction, market_price, candles_1h, [(proximal, trigger_label)], atr_4h)` — fired against the live index price, not the zone-anchored `entry` — still requires a closed-1H sweep-and-reclaim of the zone's proximal edge followed by a LATER closed candle breaking the sweep candle's opposite extreme (an engulf/BOS-style confirmation); a level touch alone is never enough. **New: Chased Entry guard.** `chase_distance` (how far `market_price` has already moved past the zone, in the trade's own direction) is capped at `chase_limit = max(0.35*ATR1H, 0.50*zone_width)` — exceeding it without a genuine `liquidity_swept` sweep force-cancels `entry_confirmed` and appends `"CHASED ENTRY blocked: waiting for price to return to the 1H RTM Base"`, so a late-discovered zone that price has already run away from can't trigger a same-tick entry far from its own proximal line. `_apply_rtm_opposing_zone()` (unchanged) then finds the nearest credible RTM zone on the OPPOSITE side (score≥50, touch_count≤2) and either caps the target at it or blocks the trade outright ("Path to 2R" in the panel) if it sits closer than the 2R floor — this opposing-zone check now runs **only inside the "zone found" branch**, against the RTM-zone-anchored `entry`/`stop`/`target`; it used to run unconditionally under `thales_eligible`, capping the plain structural-baseline target even with no same-direction RTM zone yet found, so a bare Watch/Armed setup (no RTM zone) no longer gets an opposing-zone path-clear check at all — only a setup with its own RTM entry zone does.

  **Breakout-Retest is now subordinate to the 1H RTM entry engine, with a new "Missed Entry" outcome.** `evaluate()` builds both directions' RTM base candidates (`_rtm_zone_candidates("long", ...)` / `_rtm_zone_candidates("short", ...)`, confluence-optional as above) *before* calling `_breakout_retest_setup(candles_4h, candles_1h, entry, rtm_zones=raw_rtm_long + raw_rtm_short)` — previously that method only took price/candle args and worked purely off a synthetic `±0.25*ATR`/`±0.001*index_price` tolerance band around the broken 4H level. It now looks for the nearest same-direction, score≥50 RTM base that formed at/before the breakout candle and sits on the correct side of the broken level (supply base for a short breakout, demand base for a long one); when one exists, that base's own full wick-to-wick range (`zone_definition: "full_wick_range"`) *replaces* the synthetic tolerance band as the retest/rejection zone, and the invalidation stop is widened to cover the whole base rather than just the breakout candle's own high/low. This stops a late chase entry from being placed below an RBD/DBD supply base (or above a DBR/RBR demand base) that price has already retested past. If a later closed candle actually confirms the retest/rejection (BOS/engulf) but that confirmation candle is *not* the most recent closed candle — i.e. price already departed the RTM zone before the bot could act — the setup is stamped `entry_missed=True`: `state`/`plan_status` become `"missed"` instead of `"active"`/`"triggered"`, `reason` gets `"RTM Base entry already departed: recorded as MISSED ENTRY; no lower chase signal"`, and `breakout_official_eligible`/`breakout_shadow`/`breakout_watch` are all forced false (a missed entry is recorded for audit, never promoted to a tradeable state). When RTM-linked, `trigger_basis` reads `"1H RTM <STRUCTURE> Base retest (full wick range)"` instead of the generic `"Broken 4H structure retest"`, `rtm_score`/`rtm_zone` on the signal record are overwritten from the linked base (so a breakout plan doesn't misreport RTM Score 0 while genuinely retesting a recognised base), and a `reason` line documents the link (`"Breakout-Retest linked to 1H <STRUCTURE> zone <low>-<high>; late chase entry is blocked"`). The Delta Chart's Signal Bot panel title reads `"MISSED ENTRY <DIRECTION>"` for this state (see the Signal Bot checkbox notes below).

  **`kind`/`entry_model` resolution:** `official_eligible` requires a first-touch zone (`touch_count==1`), RTM score≥65, a clear path, and a confirmed entry trigger (`entry_model="ftb_confirmed"`); `reclaim_shadow` is the same minus the BOS confirmation (swept+reclaimed only, `entry_model="ftb_reclaim_shadow"`); `later_touch_shadow` is a confirmed entry on a zone touched ≥2 times (`entry_model="later_touch_shadow"`, no longer a genuine first-touch-bounce). An `official_eligible` row is only actually stored as `kind="official"` if weekly capacity allows — at most 3 officials per asset per UTC week (Monday-anchored, `pg_advisory_xact_lock(hashtext("dankbit-signal-week-<asset>-<week_start>"))` serializing concurrent cron runs against the same check), no other `official` row for that asset currently `state="active"`, and an 8-hour post-`closed_at` cooldown per asset — failing capacity downgrades it to `shadow` instead of dropping it, with the specific capacity reason (weekly limit / active official / cooldown) appended to `reason`. `state` is `active` (official), `watch` (shadow), `armed` (`thales_eligible` but not yet a stored trade — a real, panel-visible "setup detected, entry gates being watched" state), or `rejected` (an earlier gate failed) — `armed`/`rejected` only ever pair with `kind="no_trade"`, so they're both permanently excluded from the forward-test report's own `kind in (official, shadow)` domain (see `/api/signal-bot/report` below). Every per-asset evaluation runs inside its own savepoint + broad `except Exception: _logger.exception(...)`, so one asset's failure can't block the other's row for that hour.

  **`check_outcomes()`** — separate hourly cron, resolves every `official`/`shadow` row still `state in (active, watch)` against real subsequent closed 1H candles (the still-forming last bar is always dropped, matching `_entry_trigger()`'s own convention): target hit → `tp` (`result_r` = the row's own planned `risk_reward`), stop hit → `sl` (`result_r=-1.0`), both in the same candle → `ambiguous` (exit at entry, `result_r=0.0`, a same-bar TP/SL ordering that can't be disambiguated from candle data alone), or — with no TP/SL and `expires_at` (24h from creation) passed — `expired` (marked-to-current-index-price `result_r`). `kind="no_trade"` rows are never touched by this cron regardless of `state`.

  Each accepted anchor is placed at index `expiry_index * candles_per_day` (`candles_per_day = {"1h": 24, "4h": 6, "1d": 1}[timeframe]`, default 6) and its own `confidence` (0–100, from `preview["confidence"]`/`next_row.confidence`) is carried alongside its open/high/low/close into `_compose_unified_forecast()`. That function has since been rewritten twice: first from an original "correct intermediate candles toward each anchor's raw absolute open" approach (which let raw bodies compound freely past the last anchor and could manufacture an oversized, uncontrolled tail even at low confidence) to a confidence-weighted, cumulatively-capped composition; then, in a later design pass, to its current **confluence-calibrated, propagating-anchor overlay** model — EA1/EA2/EA3 keep their independently revised Option-Flow bodies, but a same-direction confluence of Gamma-Band Consensus, Greek Flow, and Smart Liquidity may calibrate (never reverse) that body, and the reliable share of it now crossfades into the candles bridging to the next anchor instead of disappearing immediately after the anchor candle itself. Each accepted anchor's own body is split into its already-known `structural_adjustment` (untouched) and a `flow_component` (the remainder). `confluence_multiplier(anchor, raw)` (`raw` being that anchor's own same-index candle from the raw 18-candle path) can scale up, but never invent or reverse, that flow component: no boost at all if the anchor has no net direction, if its own `greek_flow_score` disagrees with that direction, or if the raw path's own candle at that index has a (nonzero) opposing direction; otherwise it counts up to 3 independent confluences read off that raw candle's own per-step diagnostic fields (the same fields `dankbit.forecast.log` persists) — Gamma-Band Consensus (`gb_all_aligned` plus a matching `gb_consensus_direction` counts as 3; `gb_consensus_direction` alone counts as 1), Greek Flow impulse sign agreement (+1), and Liquidity impulse sign agreement (+1) — mapping 3/4/5 total confirmations to a 1.03x/1.07x/1.20x multiplier (0-2: no boost), capped at 1.10x whenever either the anchor or the raw candle is itself weekend-flagged, then scaled toward 1.0 by the anchor's own `reliability()` (`(revision/max_revisions) * (confidence/100) * quality_weight`, clamped 0-1 — the same `quality_weight` an anchor's own `quality_tier` carries, see above, so a `"partial"`/`"stale"` anchor's boost is scaled down twice over: once here, once again by `confluence_multiplier`'s own scaling) so an early-revision, low-confidence, or degraded-quality anchor only receives a fraction of the proposed boost. `proposed_body = structural_adjustment + flow_component * multiplier` is no longer drawn directly — `calibrated_body = raw_body + quality_weight * (proposed_body - raw_body)` (`raw_body` being that anchor's own same-index candle's plain `close - open` off the raw 18-candle path) blends the two by the anchor's own `quality_weight` instead: a `"valid"` anchor (`quality_weight=1.0`) draws the fully-calibrated body exactly as before, while a `"partial"`/`"stale"` anchor bends the raw path's own body only in proportion to how much its own Option-Flow data can be trusted, rather than fully overriding it. `calibrated_body` is what the anchor candle's own geometry now draws (still chained off the running `open`, same as before — only the shape, never an absolute price, was ever reused). That calibrated flow component, scaled once more by `reliability()`, becomes the anchor's `reliable_flow` — and, unlike every prior version of this function, doesn't stop mattering once the anchor candle itself is drawn: every filler candle between two anchors (or before the first / after the last) now receives a small overlay linearly blended from its neighboring anchor(s)' own `reliable_flow` by position within that segment (a post-last-anchor filler instead decays that one anchor's `reliable_flow` linearly to zero across the tail); `overlay = 0.35 * blended_flow`, capped at `±0.12 * effective_atr` (that filler's own ATR off the raw path), and damped to 25% strength — never dropped or sign-flipped — whenever it disagrees with the filler's own already-computed raw body direction, so the raw path's own directional call is respected, just muted. There is deliberately no more snap-back correction toward any anchor's own absolute `open` price at all — a persistent same-direction flow reading is now allowed to compound across the bridge instead of being cancelled out to force the path back onto each anchor's independently-computed level. - `delta.py` / `gamma.py` / `theta.py` / `vega.py` — Pure Black-Scholes functions. Dollar gamma is `Γ × S²`. No side effects. Each module's `portfolio_*()` (`portfolio_delta`/`portfolio_gamma`/`portfolio_theta`/`portfolio_vega`) skips any trade with `iv == 0` before computing `T`/sigma (`if trd.iv == 0: continue`) — `iv=0` is bad/missing Deribit data, not a genuine zero-vol trade, and without the skip the function's own `sigma_eps` floor (`bs_gamma`'s is `1e-4`) turns even a trivially small trade into a razor-thin, multi-hundred-million-dollar gamma/delta/theta/vega spike right at its own strike (gamma/vega scale ~`1/sigma` near the money) — `gamma.py`'s comment is the canonical explanation the other 3 modules point back to. The same `iv <> 0` condition is also applied at the SQL level in `main.py`'s raw-SQL trade aggregation queries (`chart_png_all`, `chart_png_until`, `delta_zero_json`, `delta_zero_all_json`, `_delta_zero_for_calendar_day`), so bad-IV trades are excluded from those curves/crossings before they ever reach Python, not just inside the portfolio functions.

  **Important — always ignore `iv = 0` trades, at every fetch site, not just inside `portfolio_*()`.** This is now applied everywhere in the addon that fetches `dankbit.trade` rows destined for a gamma/delta/theta/vega curve, a per-leg Greek, or a volatility aggregate — both raw SQL (`AND iv <> 0`) and ORM (`("iv", "!=", 0)` in the domain). Raw-SQL sites: the 5 above, plus `dankbit.forecast.snapshot.get_forecast_points()`'s own trailing-window average-IV query (feeds `sigma_annual`, the forecast cone's width — not a Greek directly, but a zero-IV row dilutes that volume-weighted average the same way it'd spike a Greek, so it gets the same filter), plus `gamma_horizon_json`'s two queries (the distinct-expiration lookup and the hourly-aggregated trade query — both feed `gamma.portfolio_gamma()`) and `controllers/strategy_radar.py`'s `option_strategy_radar_json` (its distinct-expiration and per-trade queries — the latter feeds an approximate payoff, not a Greek curve, but keeps the filter for consistency). ORM sites: `main.py`'s `chart_png_hours` (`/<instrument>/<hours>`), `chart_png_zones` (`/<instrument>/zones`), `_chart_png_single_leg` (backing `/lp`/`/lc`/`/sp`/`/sc`), every expiry mode (ordinal Nearest/+1/+2, isolated Weekly/Monthly, and cumulative All) of `four_leg_gamma_json`; `dankbit.bands._compute_asset()` — the highest-blast-radius site, since it's the hourly-cron path that persists `gamma_band`/`delta_band`/`high_resistance`/`low_support`, so one bad-IV trade there used to be able to poison every downstream reader (the Delta Chart's Bands lines, the zones boxes, the Signal Bot, and the Thales Forecast engine) until this was added; and `dankbit.forecast.snapshot._trade_weighted_per_leg_fields()` (defense-in-depth — `forecast.trade_weighted_per_leg_greeks()` already guards this in Python too, see `forecast.py`). **Any new query added later that feeds a Greek calculation must carry this same filter at the fetch site** — the `portfolio_*()` in-function guard is a safety net for recordsets that genuinely can't be filtered up front (e.g. `wizard/plot_wizard.py`/`wizard/zones_wizard.py`'s `browse(active_ids)` on a user-selected backend record, which has no domain to filter), not a substitute for filtering everywhere else.
- `options.py` — `OptionStrat` class. Accumulates legs, then `plot()` returns a matplotlib `Figure`; `plot_zones(longs_curve, shorts_curve, index_price, title)` renders the Longs/Shorts zones chart from two separately-accumulated `OptionStrat` instances — `title` is accepted (callers pass `"Zones"`) but does not appear in the rendered title, which is always just `"{name} | {now} UTC"`. Uses Agg backend; do not import `pyplot` here. `build_zone_curves(instrument_name, index_price, trades, from_price, to_price, steps)` is the shared Longs/Shorts curve-building + crossing-based ±$2000 zoom logic (module-level function, not a method) — used by both `chart_png_zones` and `dankbit.bands._compute_asset`, so the PNG chart, the persisted bands record, and the live zones-box lookup can never compute different values for the same trades. `find_zero_crossings(STs, curve)` is the shared zero-crossing finder (linear interpolation on each sign change) used by `build_zone_curves`'s own Longs-vs-Shorts crossing and by `_compute_asset`'s per-curve box-boundary crossings. `zone_summary(STs, longs_curve, shorts_curve)` computes `seller_max_profit`/`buyer_max_loss`, the `high_zone`/`low_zone`/`middle_zone` boundaries, and `high_resistance`/`low_support` — from an already-built pair of curves, used by `chart_png_zones` to populate the zones-PNG page's top-left info overlay (see Zones chart above). Current price is deliberately not a parameter of this function at all: `high_zone`/`low_zone` are each curve's own highest (`high_zone`) or lowest (`low_zone`) zero-crossing — a zone forms from a single curve's crossing alone (returned as a degenerate `(price, price)` pair, rendered by `chart_png_zones` as one number rather than a range) if the other curve never crosses zero; `None` only when neither curve crosses zero at all. `middle_zone` is the min/max of `seller_max_profit`/`buyer_max_loss` instead — always defined (those two are argmax/argmin over the full curve, not zero-crossings), same degenerate-single-price rendering when they coincide. `high_resistance`/`low_support` are simply the highest/lowest Longs-vs-Shorts crossing, same reasoning (see Models, `dankbit.bands`). A separate, differently-shaped computation in `dankbit.bands._compute_asset` (needs the 4 raw box fields individually rather than a summarized pair, and doesn't need `seller_max_profit`/`buyer_max_loss` at all since it doesn't persist them) duplicates the same box/intersection logic rather than sharing this function, but both apply the identical "ignore index price, use each curve's own extremes" rule. `delta_saturation_price(STs, trades, fraction, stop_at)` finds the interpolated price where `delta.portfolio_delta(STs, trades)` first reaches `fraction` of its own extreme value at the `stop_at` edge (`'min'`/`'max'`) of `STs` — the point where a leg's sigmoid-shaped delta curve stops curving and flattens into a straight line (deep enough ITM to "trade like synthetic stock"). Relative to the curve's own extreme, not an absolute delta value, since `portfolio_delta` sums `sign*amount*per-contract delta` across every matching trade — its scale reflects total traded size (can be in the hundreds), not a single option's `[-1, 1]` range, so a fixed absolute threshold would be crossed almost immediately near the start of the curve rather than at any deep-ITM point. Curves are monotonic per leg (see `delta.py`'s sign convention), so the `stop_at` edge value is genuinely the curve's extreme in this window and its sign is inherited automatically — no separate sign parameter needed. Falls back to the `STs` edge on `stop_at` if the extreme is `0` or the curve never reaches that fraction within the window. Shared by `dankbit.bands` (`delta_band`) and the `/<instrument>/lp,lc,sp,sc` single-leg routes' green marker line, so the two can never disagree on where this point is. `DELTA_SATURATION_FRACTION = 0.9` is the single source of truth for that fraction — `main.py`'s `ChartController.DELTA_SATURATION_FRACTION` is just `options.DELTA_SATURATION_FRACTION` re-exposed as a class attribute (for `_LEG_ROUTES`). `per_leg_greeks(STs, trades, r=0.0)` computes, for each of the 4 legs split out of `trades` (`long_call`/`long_put`/`short_call`/`short_put`), where that leg's own portfolio gamma/theta/vega curve peaks or bottoms (long positions: gamma/vega peak via `argmax`, theta troughs via `argmin` since long theta is negative decay; short positions: gamma/vega bottom via `argmin`, theta peaks via `argmax` since short theta is positive decay gain) and the price/value where its portfolio delta first saturates (via `delta_saturation_price`, calls at the high-`S` edge, puts at the low-`S` edge, independent of long/short) — returning `{leg_name: {"trades", "gamma_price", "gamma_value", "delta_price", "delta_value", "theta_price", "theta_value", "vega_price", "vega_value"}}`, raw/unscaled. A leg with **zero trades** short-circuits before any curve math: `*_price` fields are `None` (a genuine "no curve" sentinel, not a price-grid-edge value) and `*_value` fields are `0.0` (genuinely zero exposure) — without this, `portfolio_gamma/theta/vega` on an all-zero trade curve returns an all-zero array, and `np.argmax`/`np.argmin` on an all-zero array both silently return index `0`, which would report `STs[0]` (the configured price-range floor) as a fake extremum instead of genuine absence. Callers needing a single "absent" sentinel collapse `None` to `0.0` themselves — `forecast.per_leg_greeks()` does this for all 16 `*_price` fields it exposes (`... or 0.0`), since those feed Odoo `Float` columns on `dankbit.bands` that can't store `None`, and `0.0` is this addon's existing absent-price convention elsewhere (e.g. `smart_liq_upper_price`). `chart_png_zones` instead renders a `None` price as the literal string `"n/a"` (via a small `_price()` helper) rather than `"$0"`, for all 16 gamma/delta/theta/vega buyer/seller call/put price lines. The since-removed `option_type_gamma_extreme(STs, trades, option_type, r=0.0)` — combined buy+sell portfolio dollar-gamma peak/bottom for one option_type across all trades — used to back the Gamma Chart's "Calls"/"Puts" combined violet lines; both `/4l/<asset>` and the since-removed `/mwa/<asset>` derived a single client-side "AVG" line from the 4 leg prices instead once those violet lines were dropped, so this helper was deleted rather than left unused — `/4l/<asset>`'s own "AVG" line (and the heavier "ALL AVG" all-expiries line that followed it) were later removed too per a further product decision, then the plain AVG line (not ALL AVG) was restored per a still later product decision (see TradingView Chart Notes). This is the single source of truth for this computation — `chart_png_zones`, `dankbit.bands._compute_asset`'s `gamma_band`/`delta_band` computation, and `forecast.per_leg_greeks` all call this one function and apply only their own display scaling on top (`chart_png_zones`'s Value lines divide gamma/delta/theta/vega by `1e6`/`10`/`1e4`/`100`; `forecast.per_leg_greeks` does the same for its `*_abs` fields; `dankbit.bands` averages the 4 gamma/delta prices into `gamma_band`/`delta_band` with no scaling at all). `forecast.trade_weighted_per_leg_greeks(trades, index_price, open_interest)` is a **forecast-only alternative** to this function (not called by `chart_png_zones` or `dankbit.bands` — those two keep using `options.per_leg_greeks()` unconditionally), ported at the explicit request of Thales's original indicator author from his own live-dashboard reference implementation (`ThalesFeatureBuilder.build`/`_max_level`): rather than finding where each leg's *aggregated* portfolio Greek curve peaks/bottoms over a synthetic price grid, it finds, within each of the 16 buyer/seller × call/put × gamma/delta/theta/vega buckets, the single *trade* whose own `amount * open_interest[instrument] * |per-contract Black-Scholes greek|` (evaluated at `index_price`, that trade's own strike/time-to-expiry/iv via `bs_gamma`/`bs_delta`/`bs_theta`/`bs_vega`) is largest — that trade's own strike becomes the reported price level. His own reference implementation evaluates the equivalent per-contract greek via a live Deribit order-book lookup (one REST call per instrument); this port uses this addon's own analytic Black-Scholes functions instead, avoiding an extra live round-trip per instrument on every forecast computation. `None` for any leg no trade contributed to (not a fake price-range-floor value). Gated behind `res.config.settings`' `forecast_trade_weighted_greeks` toggle (default off, see Settings fields below) — when off, `dankbit.forecast.snapshot.compute_and_persist()` uses `dankbit.bands._compute_asset()`'s own per-leg fields unchanged, exactly as before this toggle existed. **Calibration note:** the resulting `*_abs` values are on a different numeric scale than `per_leg_greeks()`'s own (a trade-prominence score in bespoke units vs. a scaled dollar-Greek-curve extremum) — every downstream engine that reads `*_abs` fields (`vega_regime`, `market_maker_gamma_contest`, `smart_synthetic_liquidity`, `greek_flow`, `session_activity_score`) was tuned against the default extraction's scale, so this toggle should be validated against real forecast accuracy (`dankbit.forecast.log`) before relying on it, per the source demo's own README caveat that outputs need calibration against real backtesting before analytical use.

Every branch logs its outcome (`_logger.info`/`.warning`) with the reason string, for after-the-fact review of why a given hour did or didn't confirm.
- Every hour: `compute_snapshot()` (on `dankbit.live.band`, `dankbit_compute_live_band_cron`) — loops BTC/ETH through `compute_and_create()`, creating one new append-only row each for the nearest expiry's current reading; completely independent of every other cron in this file (separate model, separate table), including `dankbit.bands`' own "Compute Bands Snapshot" cron it mirrors the numbers of. This is the **only** path that ever writes to this model at all — data-collection only, since nothing reads this model anywhere in the addon (see Models, `dankbit.live.band`).
- Every hour: `compute_snapshot()` (on `dankbit.forecast.snapshot`, `dankbit_compute_forecast_snapshot_cron`) — loops BTC/ETH through `compute_and_persist()`, same pattern as the `dankbit.bands` cron above but scheduled independently (this model's `compute_and_persist()` calls `dankbit.bands._compute_asset()` directly rather than reading that model's persisted table, so the two crons' cadences were never coupled). Guarantees the Gamma-Band Consensus and Greek Flow engines (see TradingView Chart Notes' Thales Forecast candles) get roughly-hourly snapshot history even when nobody has the "Thales Forecast" checkbox open — `/api/forecast/<asset>`'s own live polling still calls `compute_and_persist()` too, and both write paths just upsert the same current bucket.
- Every hour: `log_forecast()` (on `dankbit.forecast.log`, `dankbit_log_forecast_cron`) — for backtesting/improving the Thales Forecast engine itself, not consumed by any page or API. Loops BTC/ETH through `dankbit.forecast.snapshot.get_forecast_points()` (see Models) and persists one row per returned candle (18 rows per asset per tick, matching `simulate_forecast`'s default `hours_ahead=72`/`step_hours=4`). Tightened from an initial 4 hours (matching `step_hours`, so each tick's candles used to land close to a prior tick's own `target_time`s) to hourly per Thales dev request, for more frequent accuracy sampling — ticks now land ~4x closer together than the candle spacing itself, so consecutive ticks' `target_time`s overlap rather than lining up 1:1; `check_accuracy()` below is unaffected by this (it just matches each row against whichever later row's `generated_at` is earliest at/after that row's own `target_time`), but the `Forecast Log` pivot view now holds ~4x the row volume for the same real-world span. Writes nothing for an asset with nothing computable yet (see `get_forecast_points`), same na-safe convention every other cron in this file follows.
- Hourly: `check_accuracy()` (on `dankbit.forecast.log`, `dankbit_check_forecast_accuracy_cron`) — backfills `actual_price`/`error`/`error_pct`/`checked_at` on every forecast-log row whose `target_time` has passed, via the self-join described in Models. Purely a measurement step for improving the Thales Forecast engine; it doesn't feed back into `simulate_forecast()` or any `forecast_*` setting automatically — reviewing the resulting error stats (e.g. via the `Forecast Log` pivot view, grouped by `hours_ahead`/`mode`) and retuning the relevant `forecast_*` setting is still a manual step.
- Every 15 minutes: `compute_and_log(timeframe='1h')` (on `dankbit.forecast.next_candle`, `dankbit_compute_next_candle_forecast_1h_cron`) — one revision tick for the currently-forming 1H target candle, for both BTC/ETH (see Models). Phase-aligned to `:00`/`:15`/`:30`/`:45` UTC (`nextcall` seeded at a clean multiple-of-15-minutes anchor — Odoo's scheduler catches up to "now" then stays locked to that phase forever) so each tick lands on the exact boundary `next_candle_forecast.revision_for_elapsed_hours()` expects, rather than an arbitrary phase from whenever the cron record happened to be created/activated — the sibling 4H/1D crons below use the same phase-alignment trick at their own coarser interval.
- Hourly: `compute_and_log(timeframe='4h')` (on `dankbit.forecast.next_candle`, `dankbit_compute_next_candle_forecast_4h_cron`) — one revision tick for the currently-forming 4H target candle. Phase-aligned to the top of every UTC hour.
- Every 4 hours: `compute_and_log(timeframe='1d')` (on `dankbit.forecast.next_candle`, `dankbit_compute_next_candle_forecast_1d_cron`) — one revision tick for the currently-forming 1D target candle. Phase-aligned to 00/04/08/12/16/20 UTC.
- Hourly, 5 minutes past the hour: `check_accuracy()` (on `dankbit.forecast.next_candle`, `dankbit_check_next_candle_accuracy_cron`) — the 5-minute offset (`nextcall` seeded at `:05`) is deliberate, so this never races the 3 compute crons above for the same instant. Backfills every not-yet-checked row whose target candle has actually closed against a real Binance candle (not another forecast row, unlike `dankbit.forecast.log`'s own self-join — see Models) — a Python loop, not raw SQL, since it needs a `dankbit.trade.get_candles()` call per (asset, timeframe) pair.
- Hourly, 10 minutes past the hour: `evaluate()` (on `dankbit.signal`, `dankbit_signal_bot_evaluate_cron`) — the Signal Bot's own decision tick, one BTC + one ETH row per hour (skipped if a row for that asset/hour already exists). The `:10` offset (`nextcall` seeded at `2020-01-01 00:10:00`) lands after the top-of-hour 4H Next Candle Forecast tick above and the `:05` accuracy check, so `evaluate()` always reads that hour's freshest E1/E2/E3 anchors rather than racing them.
- Hourly, 20 minutes past the hour: `check_outcomes()` (on `dankbit.signal`, `dankbit_signal_bot_outcome_cron`) — resolves `active`/`watch` official+shadow signals against real subsequent closed 1H candles (target/stop/expiry) or leaves them open for the next tick. The `:20` offset keeps it clear of `evaluate()`'s own `:10` tick for the same hour.

## WebSocket Service (`dankbit_ws_service/`)

Single file: `dankbit_ws_batch.py`. Authenticates with `DERIBIT_KEY`/`DERIBIT_SECRET` env vars using `client_credentials` grant before fetching instruments. Reconnects every 3 seconds on any failure. Rate-limit (`over_limit`) errors trigger a 0.5s sleep and retry.

The DB connection uses `autocommit=True` — no explicit transaction management needed.

## Odoo Gotchas

- **Manifest licence field:** Odoo only accepts a fixed set of strings. Use `"Other OSI approved licence"` (British spelling) for MIT — `"MIT"` alone will fail validation.
- **Every route in this addon is `auth="user"` — login required:** a logged-out request to any URL here — PNG chart, JSON API, or TradingView page — is redirected to `/web/login?redirect=<path>` instead of rendering/responding. This includes the JSON APIs the TradingView pages' own client-side JS calls (`four-leg-gamma`, `bands`, `klines`, `zones-box`, etc.) — those rely on the browser's session cookie being sent automatically on same-origin `fetch()` calls once the user is logged in to view the page at all, so no separate handling was needed there. Testing this matters: `odoo shell` runs as superuser (no check at all), and a browser tab already logged into the backend renders every route fine regardless of this restriction — only a cookie-less request (e.g. plain `curl`) actually exercises the login redirect.
- **Model writes reached from a controller still need `.sudo()` for non-internal sessions:** every model in this addon except `dankbit.trade` only has `ir.model.access.csv` rules for `base.group_user` (internal users) — no portal grant. `auth="user"` guarantees a logged-in session, but not necessarily an internal one — a portal user would still lack write access. Reading via raw SQL (`request.env.cr.execute(...)`) bypasses this entirely, but any `self.search()`/`self.create()`/`record.write()` call reached from a controller needs an explicit `.sudo()`, or it 403s for a logged-in-but-non-internal session. This is easy to miss in testing since `odoo shell` and an already-logged-in backend browser tab both run as an internal/admin user, masking the gap. See `dankbit.bands._persist_extrema()` for the fix.

## Odoo Module Reload

Python changes to `my_addons/` take effect after `docker compose restart web`. XML/view changes and new model fields require upgrading the module:

```bash
docker compose exec web odoo -d <db_name> -u dankbit --stop-after-init
docker compose restart web
```

**Migrations (`my_addons/dankbit/migrations/`):** version-numbered pre/post-migrate scripts, keyed off `__manifest__.py`'s `version` field (currently `18.0.0.0.69`) — on `-u dankbit`, Odoo runs any migration folder whose version sits between the database's last-recorded module version and the new one, in order. Used here for four purposes: (1) backfilling a newly-added column on existing rows around a schema change — `18.0.0.0.7/post-migrate.py` sets `expiry_index = 0` on legacy `dankbit.forecast.snapshot`/`dankbit.forecast.next_candle` rows; `18.0.0.0.12/post-migrate.py` tags legacy `dankbit.live.band` rows `expiry_index = 0` (documented as "keeping them as E1", since pre-multi-expiry history was always a nearest-expiry-only reading) and recovers their `expiration` via a raw-SQL join against `dankbit_trade` on the instrument prefix recovered from `name` (`SUBSTRING(name FROM '^[^-]+-[^-]+')`); `18.0.0.0.8/pre-migrate.py` drops the old single-expiry SQL unique constraints (`dankbit_forecast_snapshot_asset_bucket_uniq`, `dankbit_forecast_next_candle_asset_timeframe_target_revision_uniq`) before the model's own `_sql_constraints` recreates the widened multi-expiry version on module load, avoiding a constraint-name collision; (2) flipping `ir_cron` `active` flags on an already-existing database, since `ir_cron.xml`'s `noupdate=1` means the file's own `active="True"` only takes effect on a fresh install (see Scheduled crons above) — `18.0.0.0.8/post-migrate.py` activates the 3 Next Candle Forecast timeframe crons plus their accuracy-check cron via raw SQL against `ir_cron`/`ir_model_data`; `18.0.0.0.18/post-migrate.py` activates the Bands/Live Band/Forecast Snapshot/Forecast Log/Forecast Log-accuracy crons via `env.ref(xmlid, raise_if_not_found=False).write({"active": True})`, logging a warning instead of failing if an xmlid is missing; (3) resetting a live-configured `ir.config_parameter` value on an already-existing database — `18.0.0.0.28/post-migrate.py` upserts `dankbit.forecast_flow_imbalance_body_damping`/`dankbit.forecast_zone_brake_min_body_mult` (and their `eth_` mirrors) back to `"0.0"`/`"1.0"`, restoring the pre-damping Forecast body defaults (see `_forecast_quality_warning` above — a low-quality-but-*not*-extreme path is now surfaced as a warning instead of being silently flattened via damping, so these two multipliers were reset to a no-op baseline on existing DBs to match; a fresh install already gets these defaults from the field's own `default=`, so only existing databases need the explicit reset); and (4) adding indexes to `dankbit_trade` directly via raw SQL — `18.0.0.0.51/post-migrate.py` adds a GIN trigram index on `name` (`gin_trgm_ops`, via the `pg_trgm` extension — a plain btree can't serve the case-insensitive `ILIKE '<asset>-%'` pattern used everywhere in this addon, both raw SQL and the ORM's `=ilike` domain operator, but a trigram index can with no query rewrite needed) plus plain btree indexes on `deribit_ts` and `expiration`, all 3 via `CREATE INDEX CONCURRENTLY` so building them can't block the WS ingestion service's own inserts (the connection is dropped into autocommit for the migration's duration — `cr._cnx.set_isolation_level(0)`, restored after — since `CONCURRENTLY` can't run inside a transaction block). Added because `dankbit_trade` had no index beyond the PK/`deribit_trade_identifier` uniqueness constraint, so every trade-window query in this addon (`_compute_asset` chief among them — called several times per Delta Chart page load/poll: once directly per tracked expiry, again inside `dankbit.forecast.snapshot.compute_and_persist()`) was a full sequential scan against millions of rows; measured via `odoo shell` before/after, `_compute_asset`'s own `Trade.search()` dropped from ~760ms to ~2ms and `_distinct_expirations` from ~800ms to ~1ms on a ~4M-row table — this was the dominant cost of Delta Chart slowness, not the actual Black-Scholes curve math (`build_zone_curves`/`per_leg_greeks` together run in well under 200ms) and not concurrent-user load. This migration is additive/idempotent (`IF NOT EXISTS` throughout) and does not require a field-level `index=True` declaration on `trade.py` — deliberately so, since that would make Odoo's own schema init also attempt a duplicate, blocking (non-`CONCURRENTLY`) index on the same `-u` upgrade. Bump `__manifest__.py`'s `version` whenever a new migration folder is added, or Odoo won't know to run it.
